## 1. 해결하려는 문제

> 채택 전 배경. 아래에 인용한 규칙 16·I-18 문구는 Task 2I-A 시점의 것이다.

FR-2.9 와 I-18 은 "같은 멱등키의 요청은 상태를 한 번만 바꾸고, 이후 요청은 최초 결과를 받는다" 를 요구한다.
당시 CLAUDE.md 규칙 16 은 그 경계를 다음으로 고정했다.

```text
TX0 키 확보 (REQUIRES_NEW) → TX1 본 작업 → TX2 결과 기록 (REQUIRES_NEW)
```

이 순서에는 **TX1 커밋과 TX2 기록 사이에 결과가 어디에도 없는 구간**이 있다. 그 구간에서 프로세스가 죽으면

- 좌석과 quota 는 이미 바뀌었는데 키는 `IN_PROGRESS` 다
- 리스가 만료되면 인수자는 "결과가 없으니 실행되지 않았다" 고 보고 **본 작업을 다시 실행한다**

당시 I-18 보장 메커니즘 3번은 "재실행되어도 조건부 UPDATE 가 `affected=0` 이므로 안전하다" 고 말했다.
**선점에서는 이것이 성립하지 않는다** — 실험에서 두 가지로 깨졌다 ([TASK-002I-A](../experiments/TASK-002I-A-hold-idempotency-contract.md) §4 RED-1·2).

| 재실행 시점의 좌석 | 결과 | 깨지는 것 |
|---|---|---|
| 여전히 첫 홀드가 잡고 있음 | 좌석 CAS 가 0 건 → `SEAT_UNAVAILABLE` 을 **최초 결과로 기록** | 결과 유실. 사용자는 좌석을 잡고도 영원히 실패를 받는다 (규칙 17) |
| 첫 홀드가 해제·만료돼 `AVAILABLE` | 재실행이 **새 홀드로 다시 선점을 커밋** | 한 키에 상태 변경 2회 (I-18) |

CAS 는 "같은 행을 두 번 같은 방향으로 바꾸지 않는다" 를 보장할 뿐, "이 요청이 이미 성공했다" 를 기억하지 않는다.
**최초 응답 재생과 좌석 CAS 의 자연 멱등성은 다른 성질이다.**

두 번째 문제는 **리스 만료가 구 작업자의 종료를 뜻하지 않는다**는 것이다. GC 정지·네트워크 지연으로 늦어진 구 작업자는
리스를 빼앗긴 뒤에도 TX1 을 커밋할 수 있다. fencing token 을 TX2 에서만 확인하면 구 작업자의 **결과 기록**은 막지만
**TX1 의 상태 변경**은 막지 못한다 — 실험 RED-3 에서 인수 이후에 fence 1 의 선점이 커밋됐다.

세 번째 문제는 **키 행이 삭제·재생성될 수 있다**는 것이다 (PR #28 리뷰 P2). INSERT 는 언제나 fence 1 로 시작하므로,
보존 기간이 지나 행이 지워지고 같은 키로 새 요청이 행을 다시 만들면 새 행도 fence 1 이다. 그 사이 지연됐던 과거의
fence 1 작업자가 돌아오면 **새 요청의 행에 과거 결과를 기록**할 수 있다 — 실제 MySQL 에서 `completeRejected` 가 0 건 대신
1 건을 바꿨다 (실험 RED-4). 이것은 과거 응답의 보존 기간 종료가 아니라 **새 요청의 소유권 침해**다.
fingerprint 를 조건에 더해도 같은 요청으로 키를 재사용하면 구별되지 않는다.

## 3. 선택 근거 (후보 B — 채택)

### 3.1 구조적 논증

1. **"선점 커밋" ⇔ "키 `COMPLETED`(성공 결과)"** — 같은 트랜잭션의 두 쓰기다. 커밋은 둘 다 남기거나 둘 다 지운다.
   TX1 직후 죽어도 재요청은 리스 만료를 기다리지 않고 저장된 결과를 재생한다.
2. **한 키에서 선점을 커밋하는 시도는 많아야 하나다** — 커밋하려면 키 행을
   `state='IN_PROGRESS' AND generation=:mine AND fence=:mine` 조건으로 `COMPLETED` 로 바꿔야 한다. 이 UPDATE 와
   인수 UPDATE(`fence = fence + 1 WHERE generation=:seen AND fence=:seen AND lease_until <= NOW(3)`)는 같은 행이라
   InnoDB 행 잠금이 직렬화한다.
   - 인수가 먼저 커밋 → 구 작업자의 완료 UPDATE 는 0 건 → 예외 → **TX1 전체 롤백**(좌석·quota 포함)
   - 완료가 먼저 → 인수 UPDATE 는 `state='IN_PROGRESS'` 에서 0 건 → 재생
3. **재시도 가능한 장애에서 키를 즉시 넘겨도 안전하다** — 커밋 결과를 모르더라도, 커밋됐다면 이미 `COMPLETED` 라
   리스 포기 UPDATE(`state='IN_PROGRESS' AND generation=:mine AND fence=:mine`)가 0 건이고, 커밋되지 않았다면 상태 변경도 없다.
4. **업무 실패를 TX2 에 기록해도 안전하다** — 업무 실패는 TX1 이 롤백된 경우이므로 상태 변경이 없다.
   TX2 가 실패해 키가 `IN_PROGRESS` 로 남아도 인수자의 재실행은 상태를 두 번 바꾸지 않는다.
   늦게 도착한 TX2 는 세대·fence 조건 때문에 새 결과를 덮지 못한다.
5. **과거 세대의 작업자는 새 세대의 행을 바꾸지 못한다** — 키 행은 INSERT 마다 새 `generation`(UUID)을 받고,
   인수는 같은 세대 안에서 fence 만 올린다. 따라서 소유권 `(generation, fence)` 는 한 키의 전체 수명(삭제·재생성 포함)에서
   **많아야 한 시도에게만** 현재 값이다. 삭제 전 행의 소유권을 쥔 작업자의 완료·포기·인수 UPDATE 는 재생성된 행에서
   `generation` 조건이 거짓이라 0 건이고, 성공 기록이 0 건이면 2 와 같이 TX1 전체가 롤백된다.
   삭제 전에 읽은 스냅숏으로 재생성된 행을 인수하는 것도 같은 이유로 0 건이다.
   UUID 충돌 확률은 무시할 수 있다고 **가정**한다.

### 3.2 잠금 순서와 대기 관계

| 트랜잭션 | 잠그는 것 (순서대로) | 다른 잠금을 쥔 채 기다리는가 |
|---|---|---|
| TX0 삽입 | 키 행 (중복 검사) | 아니다 — 키 행 하나뿐 |
| TX0 인수 | 키 행 | 아니다 |
| **TX1** | **quota → seat(PK 오름차순) → 키 행** | 키 행을 기다릴 수 있다. 그 상대(TX0·TX2)는 키 행만 쥔다 |
| TX2 | 키 행 | 아니다 |

- 키 행을 **마지막에** 잠근다. 기존 `quota → seat` 순서(규칙 2, TASK-002G-B)를 바꾸지 않고 뒤에 붙인다.
- TX0·TX2 는 키 행만 쥐고 다른 것을 기다리지 않으므로 TX1 과 순환을 만들 수 없다.
- 같은 키의 TX1 두 개는 같은 사용자·회차의 quota 행에서 먼저 직렬화된다. 앞선 TX1 이 키 행을 기다리는 동안
  뒤의 TX1 은 아무 키 행도 쥐지 않았다 — 순환이 없다.
- 같은 키의 요청은 앞선 TX1 의 **완료 UPDATE 후 커밋 전** 짧은 구간 동안 TX0 에서 기다린다 (실험 §5 표의 테스트 §3 세 번째 — `performance_schema.data_lock_waits` 로 관측).
  대기 상한은 `innodb_lock_wait_timeout = 3` 이고(규칙 9), 초과하면 재시도 가능한 장애다.

### 3.3 커넥션

TX0·TX1·TX2 는 **순차**다. 요청 하나가 동시에 쥐는 커넥션은 최대 1개다.
멱등 처리를 **바깥 트랜잭션 안에서 부르면 거부한다** — `REQUIRES_NEW` 가 바깥 커넥션을 쥔 채 두 번째 커넥션을 잡아,
풀이 고갈되면 서로를 기다리는 구조가 되기 때문이다. 실험 §5 표의 테스트 §5 에서 **풀 크기 1** 로 성공·재생·업무 실패·인수가 모두 끝났다.

## 4. 포기하는 것

- **TX1 이 한 문장·한 잠금 길어진다** — 선점 트랜잭션에 키 행 UPDATE 가 추가된다. 비용은 측정하지 않았다.
- **키 테이블을 좌석과 다른 저장소(Redis 등)에 둘 수 없다** — 원자성이 같은 트랜잭션에서 나온다.
- **업무 실패는 최종이다** — 같은 키로 `SEAT_UNAVAILABLE` 을 받은 뒤 좌석이 비어도 재실행하지 않는다. 다시 시도하려면 새 키.
- **재생은 현재 상태가 아니다** — 재생한 `holdId` 는 이미 해제·만료됐을 수 있다.
- **보존 기간 이후에는 최초 응답 재생을 보장하지 않는다** — 행이 삭제되면 같은 키는 새 요청으로 실행된다.
  단, **과거 세대의 작업자가 새 세대의 행을 바꾸는 것은 항상 금지**한다(§3.1 의 5). 포기하는 것은 재생뿐이다.
- **키 행에 세대 열(`CHAR(36)`) 하나가 늘고 모든 소유권 조건에 비교가 하나 늘어난다** — 비용은 측정하지 않았다.
- **업무 실패 기록(TX2) 구간의 장애는 여전히 리스 만료를 기다린다** — 성공 경로와 달리 즉시 재생되지 않는다.
- ~~규칙 16 의 문구와 다르다~~ — 채택 전 규칙 16 문구와 달랐던 점은 **C1 채택으로 현재 규칙 16 에 반영됐다** (§5).

| C3 | **규칙 21** — "409 = 좌석 경합 실패" | 같은 키가 진행 중일 때의 응답. IETF Idempotency-Key 초안은 409 를 쓴다 | 409 + `code=IDEMPOTENCY_REQUEST_IN_PROGRESS` + `Retry-After` 로 하고 규칙 21 에 "코드로 구분" 을 추가하거나, 다른 상태 코드를 정한다. HTTP 계층 작업에서 결정 |
| C4 | 수치 근거 없음 | 리스 30초·보존 24시간은 **가정**이다 | 리스는 TX1 최대 소요(잠금 대기 3초 × 문장 수)보다 길어야 한다. 실측 후 확정 |
