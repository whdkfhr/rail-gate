# ADR-015 — 로그인 액세스 토큰과 입장 토큰의 분리

> 상태: **제안** (2026-10-25, Task 2J-A). §3~§5 의 토큰 형식·검증 규칙은 이 Task 에서 **설계 확정**하고, §6 발급 방식과
> §8 의 항목은 **결정 대기**다. **구현 없음** — 검증 필터·발급 엔드포인트·서명키 설정·JWT 의존성은 아직 없다.
>
> 관련: [REQUIREMENTS.md](../REQUIREMENTS.md) FR-2.1·P-9·P-13, [INVARIANTS.md](../INVARIANTS.md) I-6·I-7·I-20,
> [ARCHITECTURE.md](../ARCHITECTURE.md) §5.2, [HOLD_HTTP_CONTRACT.md](../HOLD_HTTP_CONTRACT.md), CLAUDE.md 절대 규칙 3·4, 규칙 34
>
> **번호** — ARCHITECTURE §9 의 ADR-001~014 는 "작성 예정" 으로 제목이 정해져 있다. 그중 ADR-006(서비스 간 통신을 토큰 서명
> 검증으로 대체)·ADR-011(Redis 장애 시 fail-closed)과 주제가 닿지만 같은 결정이 아니므로, 충돌을 피해 **015** 를 쓴다.

---

## 1. 해결하려는 문제

선점 API 는 두 가지를 동시에 알아야 한다.

1. **누구인가** — P-13 의 간이 JWT 인증. 멱등키 범위·quota·홀드 소유자가 모두 이 사용자 id 에 걸려 있다.
2. **이 판매 회차에 들어와도 되는가** — FR-2.1 의 입장 토큰. 대기열을 통과한 사용자만 좌석 API 를 쓴다(I-7).

지금은 둘 다 없다. 그래서 `IdempotentHoldService` 는 사용자 id 를 명령에서 받고, 누구든 남의 id 로 남의 키 범위·quota 를 쓸
수 있다. 하나의 토큰에 두 의미를 섞거나, 서로 대신 쓸 수 있는 두 토큰을 만들면 같은 구멍이 다른 모양으로 남는다.

- 입장 토큰만으로 신원을 믿으면, 대기열이 발급한 토큰 하나로 그 사용자의 다른 기능(예약 조회·취소)까지 쓸 수 있다
- 로그인 토큰만 있으면 대기열을 건너뛸 수 있다 (I-7 위반)
- 두 토큰의 서명키·issuer 가 같으면 한쪽을 다른 쪽 자리에 넣어도 서명 검증이 통과한다

## 2. 대안 비교

| | 대안 | 판정 |
|---|---|---|
| A | 로그인 토큰 하나에 `evt` 를 추가 (입장 시 재발급) | 기각 — 신원 토큰의 수명·발급 주체(인증)와 입장 권한의 수명·발급 주체(queue-service)가 다르다. 입장할 때마다 신원 토큰을 바꿔야 하고 queue-service 가 신원 토큰 서명키를 갖게 된다 |
| B | 입장 토큰 하나로 신원과 권한을 모두 증명 | 기각 — 입장 토큰 발급자가 신원을 확인하지 않으면(대기열 등록은 로그인 전제일 뿐) 신원 근거가 없다. 입장 토큰 유출이 계정 탈취와 같아진다 |
| **C** | **두 토큰을 분리하고 서로 대신 쓸 수 없게 만든 뒤, 요청마다 둘의 사용자를 대조한다** | **선택** |
| D | reservation-service 가 queue-service 에 입장 여부를 묻는다 | 기각 — 절대 규칙 4(서비스 간 동기 HTTP 금지), I-7 의 "네트워크 호출 없이" |

## 3. 로그인 액세스 토큰 [설계 확정]

| 항목 | 값 |
|---|---|
| 용도 | **사용자 신원** 증명. 판매 회차 접근 권한은 담지 않는다 |
| 전달 | `Authorization: Bearer <token>`. 쿠키·쿼리 문자열로 받지 않는다 |
| 형식 | JWS(JWT), `alg=HS256` **만** 허용 (allow-list). `none`·RS·ES 등 다른 알고리즘은 거부 |
| 헤더 | `typ: "at+jwt"` |
| claim | `iss="railgate-auth"`, `aud="railgate-api"`, `sub`=사용자 id(10진수 문자열, 양수 `long`), `iat`, `exp`, `jti`, `token_use="access"` |
| 수명 | `exp − iat` = **30분 (가정값)** |
| 서명키 | **액세스 토큰 전용 키** `K_access`. 발급자(인증)와 검증자(reservation-service·queue-service)가 공유 |
| 검증 | 서명(`K_access`), `alg`, `typ`, `iss`, `aud` 포함 여부, `token_use`, `exp` > 현재, `iat`·`nbf` 미래 아님, `sub` 형식. 시계 오차 허용 **30초(가정)** |
| 실패 | **401** `AUTHENTICATION_REQUIRED` + `WWW-Authenticate: Bearer` |

토큰 만료는 애플리케이션 시각으로 판단한다. 규칙 7(만료 판정은 `NOW(3)`)은 **DB 행의 만료**(홀드·리스)에 대한 규칙이고,
토큰은 DB 를 거치지 않고 검증해야 하므로(I-7) 적용 대상이 아니다. 인스턴스 간 시계 오차는 허용 오차로 흡수한다.

## 4. 입장 토큰 [설계 확정]

| 항목 | 값 |
|---|---|
| 용도 | **특정 판매 회차 접근 권한** 증명 (FR-2.1). 신원 증명으로 쓰지 않는다 |
| 발급 | queue-service — 대기열에서 `ACTIVE` 가 된 사용자에게 (Phase 2) |
| 전달 | `Admission-Token: <token>` 헤더. `Authorization` 에 넣지 않는다 |
| 형식 | JWS(JWT), `alg=HS256` 만 허용 |
| 헤더 | `typ: "admission+jwt"` |
| claim | `iss="railgate-queue"`, `aud="railgate-reservation"`, `sub`=사용자 id, `evt`=판매 회차 id, `iat`, `exp`, `jti`, `token_use="admission"` |
| 수명 | P-7 의 Active 세션 TTL(수령 후 10분)을 넘지 않는다 — **10분 (가정값)** |
| 서명키 | **입장 토큰 전용 키** `K_admission`. `K_access` 와 다른 값이어야 한다 (기동 시 같으면 실패) |
| 검증 위치 | reservation-service 필터. **queue-service·Redis 로의 네트워크 호출 없이** 서명만으로 판정 (I-7, 절대 규칙 4) |
| 검증 | 서명(`K_admission`), `alg`, `typ`, `iss`, `aud`, `token_use`, `exp`, `iat`, `sub`·`evt` 형식, 시계 오차 30초(가정) |
| 실패 | **401** `ADMISSION_TOKEN_INVALID` (없음·만료·서명·형식) |
| 코드 위치 | **[제안]** claim 모델과 검증기는 두 앱의 유일한 공통 접점인 `modules/queue-token` 에 둔다 (절대 규칙 3) |

**blocklist**(ARCHITECTURE §5.2 — 취소·강제 만료 시 Redis 조회)는 이번 범위가 아니다. Redis 장애 시 정책은 ADR-011(작성 예정,
fail-closed)이 정한다. 서명 검증 자체는 Redis 와 무관하다.

## 5. 두 토큰의 관계 [설계 확정]

### 서로 대신 쓸 수 없게 하는 장치

| 장치 | 액세스 토큰 | 입장 토큰 |
|---|---|---|
| 서명키 | `K_access` | `K_admission` (다른 값) |
| `iss` | `railgate-auth` | `railgate-queue` |
| `aud` | `railgate-api` | `railgate-reservation` |
| `typ` | `at+jwt` | `admission+jwt` |
| `token_use` | `access` | `admission` |
| 전달 헤더 | `Authorization` | `Admission-Token` |

**키 분리만으로도 대체는 막힌다**(다른 키로 서명됐으므로 검증 실패). `iss`·`aud`·`typ`·`token_use` 는 키가 실수로 같게 설정되거나
나중에 키 관리 방식이 바뀌어도 용도 혼동을 막는 **두 번째 방어선**이다. 둘 중 하나만 맞아도 통과시키지 않는다.

### 요청마다 대조 (HOLD_HTTP_CONTRACT §3)

1. 입장 토큰 `sub` = 액세스 토큰 `sub` — 아니면 **403** `ADMISSION_USER_MISMATCH` (I-6: 유출된 입장 토큰을 남이 못 쓴다)
2. 입장 토큰 `evt` = 요청 좌석에서 서버가 해석한 판매 회차 — 아니면 **403** `ADMISSION_EVENT_MISMATCH`

대기열의 `event` 와 예약의 `SaleEvent` 가 같은 식별자 공간인지는 아직 정하지 않았다(ARCHITECTURE §3-1 "대기열 입장 범위").
이 ADR 은 **`evt` = `sale_event.id`** 를 전제로 한다 — 다르게 정해지면 대조 규칙을 매핑 기준으로 바꾼다 (§8 D-A3).

### 401 과 403 의 기준

| 상태 | 기준 |
|---|---|
| **401** | 자격 증명이 **없거나 믿을 수 없다** — 토큰 누락, 서명·형식·용도 불일치, 만료. 다시 로그인하거나 다시 입장해야 한다 |
| **403** | 두 토큰 모두 유효한데 **이 요청에 쓸 수 없다** — 사용자 불일치, 판매 회차 불일치. 재인증해도 같은 요청은 거절된다 |

## 6. 간이 JWT 발급 (P-13) [결정 대기 — D-A1]

P-13 은 "간이 JWT 발급 엔드포인트, OAuth 미도입" 이다. **임의의 `userId` 를 보내면 그 사용자의 토큰을 주는 방식은 운영 인증이
아니다** — 누구든 남의 토큰을 받는다. 신원 확인 수단이 필요하다.

| 안 | 내용 | 비용 |
|---|---|---|
| **A1 (권장)** | 사용자 테이블에 로그인 id 와 **비밀번호 해시**(Argon2id 또는 bcrypt)를 두고, `POST /api/auth/token` 이 비밀번호를 검증한 뒤 액세스 토큰을 발급한다. 로그인 실패는 계정 존재 여부를 드러내지 않는 같은 401, 시도 횟수 제한 | migration(사용자 테이블), 해시 라이브러리 의존성, ADR 추가 |
| A2 | 사전에 배포한 사용자별 비밀(API 키)로 서명 요청 | 사용자별 비밀 배포·폐기 절차가 필요하다. 웹 사용자에게 맞지 않다 |
| A3 | 외부 IdP(OAuth/OIDC) | P-13 이 명시적으로 제외했다 |

### 개발 전용 발급 [설계 확정 — 구현 시 지켜야 할 조건]

로컬 개발·부하 테스트에 사용자 수천 명의 토큰이 필요하면 개발 전용 발급을 둘 수 있다. 조건:

- **기본 비활성.** `railgate.auth.dev-issuer.enabled=false` 가 기본이며, 켜려면 명시적 설정이 필요하다
- **운영 프로필에서 켜지면 기동 실패** — 활성 프로필에 `local`·`loadtest` 외의 것이 있으면 시작하지 않는다
- **별도 issuer** — 개발 발급 토큰의 `iss="railgate-dev-auth"`. 운영 검증기는 이 issuer 를 거부하고, 개발 발급이 켜진
  환경의 검증기만 받아들인다. 같은 키로 서명하더라도 운영에서 통과하지 않는다
- 경로는 운영 API 와 섞지 않는다 (예: `/dev/auth/token`)

**인증·입장 검증을 건너뛰는 운영 경로는 설계하지 않는다.** "헤더가 없으면 테스트 사용자로 본다" 같은 기본값을 두지 않는다.

### 대기열 구현 전의 테스트 대역 [설계 확정]

queue-service 입장 토큰 발급은 Phase 2 다. 그 전까지 선점 HTTP 테스트는 **테스트 소스 안의 토큰 생성 도우미**가 테스트 전용
`K_access`·`K_admission` 으로 토큰을 만든다. 운영 소스에 테스트용 발급기·우회 설정을 두지 않는다.

## 7. 선택 근거와 포기하는 것

**근거** — 신원과 권한의 발급 주체·수명이 다르므로 토큰도 나눈다. 두 토큰을 서로 대신 쓸 수 없게 하면 "입장 토큰 하나로 다른
사용자 행세" 와 "로그인만으로 대기열 우회" 를 각각 서명 검증 단계에서 막는다. 둘 다 서명만으로 검증되므로 queue-service·Redis
장애가 선점 API 의 인증을 멈추지 않는다(I-20).

**포기하는 것**

- 클라이언트가 헤더 두 개를 관리해야 한다
- HS256 은 대칭키라 **검증자도 서명할 수 있다.** reservation-service 가 침해되면 입장 토큰을 위조할 수 있다 —
  ES256 등 비대칭 서명은 **[제안]** 후속 검토(§8 D-A2)
- 토큰은 만료 전까지 유효하다. 즉시 폐기는 blocklist(후속)가 생길 때까지 없다
- 토큰 만료는 애플리케이션 시각에 기대며 시계 오차 30초를 허용한다
