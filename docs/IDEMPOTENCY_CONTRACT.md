## 1. 키의 범위

멱등키는 **(인증된 사용자, 연산, 클라이언트 키)** 세 값이 모두 같을 때만 같은 키다.

| 구성 | 값 | 이유 |
|---|---|---|
| 사용자 | **인증된 주체**의 `userId`. 요청 본문 값이 아니다 | 서로 다른 사용자가 같은 키를 보내도 결과를 공유하지 않는다. 키만으로 범위를 잡으면 남의 `holdId` 를 재생받을 수 있다 |
| 연산 | `HOLD_SEATS` | 같은 키로 선점과 해제를 보내도 서로의 결과로 재생되지 않는다 |
| 클라이언트 키 | `Idempotency-Key` 헤더 값 | — |

### 클라이언트 키 형식과 비교

- ASCII 영숫자·`-`·`_`, **8~64자**. UUID 를 권장한다. 길이 범위는 **가정**이다 (측정 근거 없음).
- **바이트 단위 비교** — 대소문자를 구분하고, 공백을 다듬지 않고, 유니코드 정규화를 하지 않는다.
  서버가 값을 고쳐 같게 만들면 클라이언트가 다르다고 믿는 두 요청이 결과를 공유한다.
- 누락·형식 위반은 **400**, 키를 소비하지 않는다 (규칙 14).

## 2. 요청 fingerprint

같은 키에 **다른 요청**이 실렸는지 판별한다.

```text
fingerprint = SHA-256( "hold-seats/v1:" + 오름차순 정렬한 seatId 를 ',' 로 이은 문자열 )
```

| 규칙 | 내용 |
|---|---|
| 포함 | 버전 접두사, 좌석 id 집합 |
| 좌석 순서 | **정규화한다** — 오름차순 정렬. 선점 결과는 순서와 무관하고 저장소도 PK 순으로 잠근다. `[2,1]` 과 `[1,2]` 는 같은 요청 |
| 중복 좌석 | **정규화하지 않는다** — 명령 생성 단계에서 400. 키를 확보하기 전이라 키를 소비하지 않는다 |
| 제외 | 사용자(키 범위에 이미 있음), 판매 회차(클라이언트 입력이 아니라 서버가 좌석에서 해석) |
| 버전 | 정규화 규칙이 바뀌면 접두사를 올린다. 옛 fingerprint 와 섞이지 않는다 |

## 3. 상태와 판정

### 키 행의 상태

| 상태 | 의미 | 필드 |
|---|---|---|
| `IN_PROGRESS` | 어떤 시도가 리스를 쥐고 실행 중이거나, 실행 중 사라졌다 | `generation`, `fence`, `lease_until` |
| `COMPLETED` | 결과가 확정됐다. 이후 같은 요청은 재생만 한다 | 결과 종류와 값 |

- **generation** — 키 행의 세대. **INSERT 할 때마다 새로 부여**하고(UUID) 인수해도 바뀌지 않는다.
  보존 기간 뒤 삭제된 키가 다시 만들어지면 다른 세대다.
- **fence** — 같은 세대 안에서 키를 소유한 시도의 번호. 확보 시 1, 인수할 때마다 1 증가. 새 세대는 다시 1 부터다.
- **소유권 = (generation, fence)**. 인수·완료 기록·포기는 모두 **키 범위 + `generation = :mine` + `fence = :mine`** 을
  같은 UPDATE 의 조건으로 확인하고 `affected_rows` 로 판정한다. 앞서 SELECT 로 확인하지 않는다.
  fence 만으로는 삭제 전 행의 fence 1 과 재생성된 행의 fence 1 을 구별할 수 없고,
  fingerprint 를 더해도 같은 요청으로 키를 재사용하면 구별되지 않는다 (PR #28 리뷰 P2).
- **리스 만료 판정은 DB 의 `NOW(3)`** 이다 (규칙 7).

### 이미 행이 있을 때의 판정 — 순서가 계약이다

1. **fingerprint 불일치 → 거부** (상태와 무관). 진행 중이든 완료든, 다른 요청은 실행되지도 재생되지도 않는다
2. `COMPLETED` → **재생**
3. `IN_PROGRESS` + 리스 유효 → **진행 중** (실행하지 않는다)
4. `IN_PROGRESS` + 리스 만료 → **인수** (같은 세대에서 `fence + 1`). 조회한 스냅숏의 세대·fence 가 그대로일 때만 성공한다. 리스 만료는 기존 작업자의 종료를 뜻하지 않는다 — §5

## 4. 결과의 분류

| 분류 | 예 | 저장 | 같은 키 재요청 |
|---|---|---|---|
| **성공** | 선점 완료 (`holdId`, `saleEventId`, `seatCount`) | **본 작업과 같은 트랜잭션(TX1)** 에서 | 최초 결과 재생 |
| **업무 실패** | `SEAT_UNAVAILABLE`, `QUOTA_EXCEEDED`, `SALE_EVENT_SCOPE_REJECTED` | TX1 롤백 뒤 TX2 에서 | 같은 실패 재생. **좌석이 나중에 비어도 재실행하지 않는다** — 다시 시도하려면 새 키 |
| **재시도 가능한 장애** | 잠금 대기 초과, 데드락, 연결 실패, 알 수 없는 예외 | **저장하지 않는다.** 리스를 즉시 만료시킨다 | 다음 요청이 바로 인수해 실행 |
| **진행 중** | 다른 시도가 리스를 쥠 | — | 나중에 같은 키로 재시도 |
| **불일치** | 같은 키·다른 fingerprint | — | 항상 거부 |

재시도 가능한 장애를 저장하지 않는 이유는 **커밋 여부가 불확실할 수 있기 때문**이다. 커밋됐다면 성공 결과가 이미 같은
트랜잭션에 남아 리스 포기가 무효가 되고, 커밋되지 않았다면 상태 변경이 없으므로 재실행이 안전하다.

### 최초 응답 재생 ≠ 좌석 CAS 의 자연 멱등성

좌석 조건부 UPDATE 는 같은 좌석을 두 번 같은 방향으로 바꾸지 않을 뿐, **이 요청이 이미 성공했다는 사실을 기억하지
않는다.** 성공한 요청을 재실행하면 자기 홀드에 막혀 다른 응답(경합 거절)을 받거나, 그사이 홀드가 풀렸다면 다시
선점한다. 최초 응답 재생은 키 행에 남은 결과에서만 나온다.

**재생은 현재 상태가 아니다.** 재생한 `holdId` 는 이미 해제·만료됐을 수 있다. 현재 상태는 조회 API 의 몫이다.

## 5. 트랜잭션 경계

```text
TX0 (REQUIRES_NEW)  키 INSERT(새 세대), 또는 리스 만료 시 인수 UPDATE (세대·fence 조건)
TX1 (REQUIRED)      HoldSeatsService.hold  →  키 행 완료 UPDATE (세대·fence 조건)
                    └ 완료 UPDATE 가 0 건이면 리스를 빼앗긴 것 → TX1 전체 롤백
TX2 (REQUIRES_NEW)  업무 실패 기록 또는 리스 포기 (세대·fence 조건). TX1 이 롤백된 경우에만
```

- 세 트랜잭션은 **순차**다. 요청 하나가 동시에 쥐는 커넥션은 최대 1개다. 바깥 트랜잭션 안에서 부르면 거부한다.
- TX1 의 잠금 순서는 **quota → seat(PK 오름차순) → 키 행**이다.
- 성공 결과를 TX1 에 기록하는 이 경계는 **ADR-009 C1 채택으로 CLAUDE.md 규칙 16 에 반영됐다** (2026-10-12).
- TX2 의 업무 실패 기록은 **TX1 롤백이 확인된 경우에만** 한다. 커밋 결과가 불명이면 결과를 쓰지 않고 리스만 포기한다.

## 6. 보존 기간

- 완료된 키는 **24시간** 보존한다고 **가정**한다. 클라이언트 재시도 창과 선점 유지 시간(5분, P-4)보다 충분히 길다는 것
  외에 측정 근거가 없다.
- **보존 기간 이후에는 최초 응답 재생을 보장하지 않는다.** 행이 삭제되면 같은 키는 새 요청으로 실행된다 (실험 §5 표의 테스트 §4 마지막 항목에서 확인).
- **그러나 과거 세대의 작업자가 새 세대의 행을 바꾸는 것은 보존 기간과 무관하게 항상 금지한다.** 삭제 전에 키를 쥐었던
  작업자가 늦게 돌아와도 세대가 달라 완료·포기·인수 UPDATE 가 0 건이다. 성공 기록이 0 건이면 그 작업자의 TX1(좌석·quota)
  전체가 롤백된다. 새 요청의 fingerprint 가 같든 다르든 같다 (실험 §5-1).
- 리스는 **30초**로 가정한다. TX1 의 최대 소요보다 길어야 한다 — 실측하지 않았다.
- 삭제 작업은 구현하지 않았다. 후속 정리 계약: **`COMPLETED` 이면서 보존 기간이 지난 행만** 지운다. `IN_PROGRESS` 행은
  삭제 대상이 아니다 — 지우면 실행 중인 시도의 결과가 남지 않는다 (세대 검사는 그 작업자의 쓰기를 막지만 결과는 사라진다).

## 7. 응답 (계약만 — HTTP 계층 미구현)

> **현행 HTTP 계약은 [HOLD_HTTP_CONTRACT.md](HOLD_HTTP_CONTRACT.md) §6 이다** (Task 2J-A, C3 채택). 아래 표는 Task 2I-A·B 시점의
> 제안으로 보존한다. 달라진 점: 진행 중·소유권 상실 = `409 IDEMPOTENCY_REQUEST_IN_PROGRESS`, 회차 해석 거부 = `422`,
> 재시도 가능한 장애 = `503`, 그 외 = `500`. 재생과 traceId 는 같은 문서 §7.3 D1 결정 대기.

| 상황 | 제안 | 비고 |
|---|---|---|
| 키 누락·형식 위반 | 400 | 규칙 14 |
| 성공 (실행·재생 모두) | 201, 같은 본문 | 재생임을 알리는 헤더는 후속 결정 |
| 업무 실패 (실행·재생 모두) | 409 `SEAT_UNAVAILABLE` / 429 `QUOTA_EXCEEDED` / 400 계열 | 기존 규칙 21·22 |
| fingerprint 불일치 | 422 `IDEMPOTENCY_KEY_REUSED` | |
| 진행 중 | **결정 대기** — 409 + `Retry-After` 후보 | 규칙 21 은 409 를 좌석 경합으로 정의한다. ADR-009 C3 |
| 리스를 빼앗긴 시도 | 진행 중과 같게 | 같은 키로 재시도하면 인수자의 결과를 받는다 |
| 재시도 가능한 장애 | 503 계열 + `Retry-After` | 결과를 저장하지 않으므로 재시도가 실행될 수 있다 |

오류 응답 형식은 `{ code, message, traceId }` (규칙 24).
