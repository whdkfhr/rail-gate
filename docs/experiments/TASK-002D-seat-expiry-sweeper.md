## 1. 목적과 범위

두 불변식을 좌석 재고 수준에서 다룬다.

- **I-10** 만료된 선점 좌석은 다시 `AVAILABLE`이 된다
- **I-11** 만료 처리와 확정이 경쟁해도 **SOLD 좌석은 절대 해제되지 않는다**

I-11은 Task 2B에서 "스위퍼가 없어 미검증"으로 남겨둔 항목이다. 이번에 스위퍼가 생기면서 비로소 검증할 상대가 생겼다.

### 범위에 없는 것

`@Scheduled` 배선, 자발적 해제(FR-2.5), I-12, quota 증감, I-15 결제 승인 검증, 멱등성 키, 감사 로그·메트릭 실제 구현, REST API·포트 인터페이스, 운영 DataSource 설정. §9에 기록한다.

## 2. I-10 / I-11 구조적 방어

### 회수 SQL

```sql
UPDATE seat_inventory FORCE INDEX (PRIMARY)
   SET status='AVAILABLE', hold_id=NULL, held_by=NULL, held_at=NULL,
       expires_at=NULL, reservation_id=NULL, version=version+1
 WHERE (id, hold_id) IN ((?,?), (?,?), ...)   -- 쌍 재검증
   AND status     IN ('HELD', 'PAYING')       -- ★ SOLD 를 구조적으로 배제
   AND expires_at <= NOW(3)                   -- 만료 여부 재확인
```

| 조건 | 막는 것 |
|---|---|
| `(id, hold_id)` 쌍 | 그 사이 회수되고 **남이 새로 잡은** 좌석 |
| `status IN ('HELD','PAYING')` | **확정된 좌석** (I-11의 핵심) |
| `expires_at <= NOW(3)` | 그 사이 **데드라인이 연장된** 좌석 |

**I-11은 `status` 술어가 지킨다.** `SOLD`가 출발 상태 목록에 없으므로 어떤 후보를 넘겨도 확정된 행은 매칭되지 않는다. 이는 Task 2B에서 확정이 `expires_at`을 `NULL`로 비우는 것과 **독립적인** 두 번째 방어다. `expires_at`이 남아 있어도 상태 술어만으로 배제된다.

만료 판정은 MySQL `NOW(3)`이 한다. 애플리케이션 시각을 파라미터로 넘기면 인스턴스 간 클럭 드리프트로 판정이 갈린다(규칙 7).

## 3. 후보 SELECT와 최종 CAS를 분리한 이유

**만료 대상을 찾는 기준과 잠금 순서를 정하는 기준이 다르다.**

| | 기준 | 인덱스 |
|---|---|---|
| 후보 탐색 | `expires_at` 범위, 오래된 순 | `idx_seat_inventory_expiry_candidate` (V2) |
| 잠금 순서 | `id` 오름차순 | `PRIMARY` |

만료 후보 인덱스 순서로 곧장 잠그면 확정 경로(PK 순서)와 교차해 **데드락**이 난다(규칙 2). `V1__seat_inventory.sql`의 인덱스 주석이 이미 "후보 SELECT + 정렬 후 UPDATE 2단계"를 지시하고 있었다.

**잠금 순서는 회수 UPDATE의 관심사**이므로, 후보를 읽은 뒤 Java에서 `id` 오름차순으로 다시 정렬한다. 후보 SELECT 자체의 정렬은 전혀 다른 목적(공정성)을 가지며 바로 아래에서 다룬다.

### 후보 선택 순서 — 공정성

I-10은 "만료된 좌석은 다시 판매 가능해진다"이지만 **언제**인지는 말하지 않는다. 배치 크기가 유한한 이상 어떤 후보를 먼저 고르느냐가 실질적인 회수 지연을 결정한다. 특정 좌석이 계속 밀리면 사실상 회수되지 않는 것과 같다.

```sql
ORDER BY expires_at ASC, id ASC
```

`id`는 만료 시각이 동률일 때의 tie-breaker다. 이것이 없으면 `LIMIT` 결과가 결정적이지 않다.

**두 정렬의 목적을 혼동하지 않는다.**

| 정렬 | 목적 |
|---|---|
| 후보 SELECT의 `ORDER BY expires_at, id` | **공정성.** 어떤 만료 좌석을 먼저 처리할지 |
| 회수 UPDATE 전 Java의 id 오름차순 | **데드락 방지.** 어떤 순서로 행을 잠글지 |

후보 SELECT는 행 잠금을 잡지 않으므로 그 정렬은 잠금 순서와 **무관하다.**

#### 정렬이 없으면 무슨 일이 생기는가 (재현됨)

기존 `(status, expires_at)` 인덱스는 첫 컬럼이 `status`다. `status IN ('HELD','PAYING')`은 **두 개의 범위 스캔**이 되고, `ORDER BY`가 없으면 반환 순서가 그 스캔 순서에 좌우된다.

정렬 추가 전 실제 테스트 실패 결과:

```
가장_오래_만료된_좌석이_상태와_무관하게_첫_배치에_포함된다
  → 첫 배치 [45, 46, 47] 에 가장 오래된 좌석 44 가 없음

특정_상태만_지속적으로_우선되지_않는다
  → 첫 배치가 ["HELD","HELD","HELD","HELD"] 로 채워짐

작은_배치를_반복하면_오래된_후보부터_빠져나간다
  → [56, 58, 60, 55, 57, 59]  (상태별로 뭉쳐서 나옴)
```

한 상태의 만료 행이 배치 크기보다 많이 쌓이면 **다른 상태의 더 오래된 좌석이 매 배치에서 반복적으로 밀려난다.**

#### 인덱스 선택 — 측정 근거

`ORDER BY expires_at, id`를 기존 인덱스로 처리하면 filesort가 된다. MySQL 8.4, 20,000행(만료 후보 6,000행)에서 `EXPLAIN ANALYZE`로 실측했다.

| 인덱스 | `Extra` | 실제 스캔 행 | actual time |
|---|---|---|---|
| `(status, expires_at)` (기존) | **Using filesort** | **6,000** | **6.14ms** |
| `(expires_at, id)` (V2 신규) | 없음 | **100** | **0.254ms** |

기존 인덱스는 **LIMIT이 조기 종료하지 못하고** 만료 후보 전부를 읽어 정렬한 뒤 잘라낸다. backlog가 커질수록 비용이 선형으로 증가한다.

`expires_at`이 NULL인 `AVAILABLE`/`SOLD`는 `expires_at <= NOW(3)` 범위에서 자연히 제외되므로, `status`를 인덱스 앞에 둘 이유가 없다. 그래서 V2 인덱스에는 `status`를 넣지 않았다.

기존 인덱스는 **삭제하지 않았다.** 삭제 여부는 다른 경로의 영향까지 측정한 뒤 판단한다.

### 그 대가로 창이 열린다

후보 SELECT는 행 잠금을 잡지 않는다. 조회부터 UPDATE까지 다른 세션이 자유롭게 그 행을 바꿀 수 있다.

**이 창을 긴 트랜잭션이나 외부 락으로 막지 않는다.** 대신 후보를 현재 상태의 진실로 간주하지 않는다. 후보 조회는 **탐색**일 뿐이고, 성공 판정은 최종 조건부 UPDATE의 `affected_rows`가 한다.

### 창이 실제로 열리는 이유

```sql
-- JdbcSeatPaymentRepository.confirm()
WHERE id=? AND hold_id=? AND status='PAYING'    -- expires_at 조건이 없다
```

**이미 만료된 PAYING 좌석도 확정된다.** 결제 승인이 늦게 도착한 정상 요청이 스위퍼가 회수하려는 바로 그 좌석을 확정하는 상황은 **예외가 아니라 정상 경로**다. 이것이 I-11이 다루는 경쟁이다.

### 스위퍼는 전부-또는-전무가 아니다

다좌석 선점(I-9)과 반대다. 후보 하나가 stale하다고 나머지를 롤백하면 만료 좌석이 계속 쌓이기만 한다. 유효한 후보는 회수하고 stale한 후보는 `affected_rows`에서 빠진다. **후보 수와 회수 수가 다른 것은 오류가 아니다.**

그래서 자체 `TransactionTemplate`과 `setRollbackOnly()`를 쓰지 않는다. 되돌릴 것이 없기 때문이다. 따라서 Task 2C처럼 **내부 rollback-only가 외부 커밋에서 `UnexpectedRollbackException`으로 나타나는 문제는 만들지 않는다.**

### 그렇다고 외부 트랜잭션과 무관한 것은 아니다

`JdbcTemplate`은 `DataSourceUtils`를 통해 커넥션을 얻으므로, 같은 `DataSource` 위에 활성 트랜잭션이 있으면 **그 트랜잭션에 참여한다.** 그때는 실제 커밋 시점과 잠금 보유 시간이 외부 트랜잭션 경계에 좌우된다.

현재 저장소 단독 호출 테스트가 검증하는 것은 **autocommit 기반의 짧은 UPDATE 경로**다. 앞으로 quota 감소나 감사 로그를 이 회수와 같은 트랜잭션으로 묶는다면 **트랜잭션 경계는 애플리케이션 서비스가 소유해야 한다.** 그 트랜잭션 안에 외부 I/O를 넣지 않는다(규칙 10).

## 4. ID와 hold ID 쌍을 재검증하는 이유

```sql
WHERE (id, hold_id) IN ((?,?), (?,?), ...)     -- ✅ 쌍으로 검증
WHERE id IN (?,?) AND hold_id IN (?,?)          -- ❌ 교차 매칭
```

두 집합을 독립적으로 비교하면 **후보 A의 좌석이 후보 B의 홀드와 교차 매칭**된다. 좌석 1이 홀드 H1을, 좌석 2가 홀드 H2를 잡고 있을 때, 그 사이 좌석 1이 회수되고 H2로 다시 잡히면 `id IN (1,2) AND hold_id IN (H1,H2)`가 좌석 1을 매칭시킨다. 스냅샷과 다른 홀드인데도 회수된다.

행 생성자 `IN`은 각 `(id, hold_id)` 쌍을 함께 검증한다. 테스트에서 두 좌석의 홀드를 맞바꾼 후보를 넘겨 **한 건도 회수되지 않음**을 확인했다.

SQL 문자열에는 **플레이스홀더 개수만** 생성하고 값은 전부 바인딩한다. 구조 생성은 `expireSql(int)` 한 메서드에 격리했다.

## 5. 순진한 구현의 실패 재현

**스레드가 필요 없다.** 결함이 타이밍이 아니라 "후보 SELECT와 UPDATE 사이에 상태가 바뀔 수 있다"는 사실 자체이기 때문이다. 테스트는 그 창을 제어 흐름으로 연다.

```
1. PAYING 좌석의 expires_at 을 과거로 만든다
2. 스위퍼가 후보를 조회한다          ← 이 시점의 스냅샷
3. 확정 경로가 그 좌석을 SOLD 로 확정한다  ← 창이 열려 있다
4. 스위퍼가 UPDATE 를 실행한다
```

순진한 구현은 `WHERE id IN (...)`만 쓴다. 상태도, 홀드 소유권도, 만료 여부도 다시 확인하지 않는다.

| | 회수 보고 | 최종 상태 | `reservation_id` |
|---|---|---|---|
| 순진한 구현 | **1건** | **`AVAILABLE`** ❌ | **삭제됨** |
| 조건부 만료 | **0건** | `SOLD` ✅ | 유지 |

**확정에 성공해 사용자에게 판 좌석이 다시 판매 가능 상태가 됐다.** 예약 귀속까지 지워졌다. 오류 로그는 한 줄도 남지 않는다 — UPDATE가 정상 성공했기 때문이다.

### 확정만이 위험한 것은 아니다

만료 후 다른 사용자가 다시 잡은 좌석도 같은 문제다. 순진한 구현은 **남의 새 홀드를 파괴**한다(`AVAILABLE`로 되돌림). 조건부 만료는 `hold_id`가 다르므로 0건이다.

## 6. 확정 우선 / 만료 우선 결정적 테스트

통계적 경합만으로 끝내지 않고 두 순서를 각각 고정해 검증했다.

| 순서 | 확정 결과 | 만료 결과 | 최종 상태 | `version` 증가 |
|---|---|---|---|---|
| 확정 → 만료 | `CONFIRMED` | **0건** | `SOLD` | **1** |
| 만료 → 확정 | `NOT_CONFIRMED` | **1건** | `AVAILABLE` | **1** |

`version` 증가가 1이라는 것이 **정확히 한 전이만 성공했다**는 뜻이다. 두 UPDATE가 모두 통과했다면 2가 된다.

## 7. 동시성 측정 결과

MySQL 8.4 (Testcontainers), HikariCP max 64, `innodb_lock_wait_timeout = 3`, Java 21 가상 스레드. `CountDownLatch` 동시 출발, `Thread.sleep` 미사용.

각 라운드마다 만료된 `PAYING` 좌석을 새로 만들고 확정과 만료를 동시에 출발시킨다.

| 지표 | 값 |
|---|---|
| 경합 라운드 | **200회** |
| 확정 승리 | **134회** |
| 만료 승리 | **66회** |
| 양쪽 성공 / 양쪽 실패 | **0회** |
| I-11 위반 (SOLD → AVAILABLE) | **0건** |
| 필드 조합 위반 | **0건** |
| `version` 증가가 1이 아닌 라운드 | **0건** |
| 시스템 오류 / deadlock / lock timeout | **0건** |

승패 분포는 실행마다 달라진다(관측 예: 107/93, 134/66). **양쪽 승자가 모두 나오는 것은 경쟁이 실제로 일어났다는 정황일 뿐 테스트 유효성의 조건은 아니다.** 두 순서 각각의 정확성은 §6의 결정적 테스트가 이미 검증하며, 그쪽은 실행마다 같은 결과를 낸다.

라운드마다 즉시 검사하는 것과 별개로, 전체 실행 후 테이블 전체를 훑어 확인했다.

| 검증 쿼리 | 결과 |
|---|---|
| `SOLD`인데 `reservation_id IS NULL` (V-5 고아) | **0행** |
| `AVAILABLE`인데 잔여 필드가 남음 | **0행** |
| 경합 후 `HELD`/`PAYING` 중간 상태로 남음 | **0행** |

> **이 결과는 I-11 위반 부재의 증명이 아니다.** 이 환경과 200회 실행에서 관측되지 않았다는 **통계적 보조 근거**다(규칙 30). 구조적 논증은 §2, 결정적 재현은 §5·§6이다.

| 후보가 `expires_at` 오름차순 | 통과 |
| 만료 시각 동률이면 `id` 오름차순 | 통과 |
| 반복 조회 시 순서 결정성 | 통과 (5회 반복 동일) |
| 작은 배치 반복 시 오래된 순서로 소진 | 통과 |
| 특정 상태만 우선되지 않음 | 통과 |

`EXPLAIN` 테스트는 **운영 SQL 상수를 그대로** `EXPLAIN`한다(`FIND_CANDIDATES_SQL`, `expireSql(int)`). 테스트가 복사한 SQL과 운영 SQL이 조용히 어긋나는 것을 막기 위해 두 상수를 package-private으로 두었다.

**경계 테스트의 한계.** `NOW(3)`은 계속 흐르므로 "정확히 같은 순간"을 SQL로 고정할 수 없다. `expires_at = NOW(3)`으로 설정하고 회수되는지 확인하는 것은 경계가 배타적(`<`)이 아니라 **포함(`<=`)** 임을 보이는 것이지, 밀리초 단위 동시각을 재현한 것이 아니다.

## 9. 남은 위험과 후속 Task

### 주기 실행 배선 — 미구현 ★

`@Scheduled` 등록이 없다. **이 저장소는 한 번의 스윕만 수행하며, 아무도 그것을 호출하지 않는다.** 즉 현재 저장소에서 만료 좌석은 실제로 회수되지 않는다.

배선 시 함께 결정해야 할 것: 실행 주기와 `batchSize`(회수 지연과 DB 부하의 트레이드오프), 그리고 아래 다중 스위퍼 문제.

### 다중 스위퍼 — 정합성 문제가 아니라 효율 문제

앱을 2대 띄우면 두 스위퍼가 같은 후보를 조회할 수 있다. **그래도 정합성은 유지된다.** 최종 조건부 UPDATE가 상태·홀드·만료를 다시 검증하므로 한쪽만 회수하고 다른 쪽은 `affected_rows = 0`이 된다. §2의 구조적 방어가 그대로 작동한다.

**남는 것은 헛일과 잠금 경합이라는 효율 문제다.** 따라서 **잡 락이 정합성을 위한 필수 조건이 아니다.**

대응은 측정 후에 결정한다. 필요한 수치는 중복 실행 비율, stale 비율, DB 부하다. 지금은 셋 다 관측 수단이 없다(규칙 35 참조).

| 대안 | 성격 |
|---|---|
| 별도 락 없이 CAS에 맡김 | 현재 상태. 인스턴스 수가 적으면 충분할 수 있다 |
| 작업 범위 파티셔닝 | 인스턴스별로 후보 집합을 나눠 중복 자체를 줄인다 |
| DB 기반 lease 또는 job lock | 중복을 막지만 락이 죽으면 **스위퍼 전체가 멈추는 새 가용성 위험**을 만든다 |
| `SKIP LOCKED` 기반 분배 | 후보 조회에 잠금이 생기므로 현재의 "조회는 잠그지 않는다" 설계와 상충한다. 별도 검토 필요 |

ShedLock 같은 새 기술을 도입하려면 **ADR과 측정 근거가 먼저** 있어야 한다(CLAUDE.md 설계 결정 규칙). 이번 Task에서는 잡 락 의존성을 추가하지 않았다.

### 자발적 해제 FR-2.5 — 인프라 경로 미구현

도메인 전이(`Seat.release`)는 존재하지만 **인프라/API 경로가 없다.** 사용자가 직접 홀드를 풀 수 없어 만료를 기다리는 수밖에 없고, 좌석 회전율이 떨어진다. 해제도 `WHERE hold_id = ?` CAS여야 하며(규칙 18), 영향 행이 0이어도 204로 응답해 자연 멱등이 되게 해야 한다.

### I-12 — 미구현. quota 테이블 자체가 없다

상태 전이와 quota 연동을 구분해야 한다.

| 항목 | 상태 |
|---|---|
| `PAYING → SOLD` 확정 상태 전이 | **구현됨** (Task 2B) |
| 확정 시 quota 감소 연동 | 미구현 |
| 만료 상태 전이 | **구현됨** (Task 2D) |
| 만료 시 quota 감소 연동 | 미구현 |
| 자발적 해제 도메인 전이 | **존재** (`Seat.release`) |
| 자발적 해제 인프라/API 경로 | 미구현 |
| `user_hold_quota` 테이블 | 미구현 |

I-12를 구현할 때는 선점 시 quota 증가뿐 아니라 **SOLD 확정·만료 회수·자발적 해제에 대응하는 quota 감소를 같은 트랜잭션 경계에서 연동**해야 한다. 확정과 만료 상태 전이는 이미 존재하지만 quota 감소 연동이 없고, 자발적 해제는 인프라 경로부터 없다.

### 규칙 32 감사 로그 — 미구현

`seat_state_log`가 없다. 만료 회수는 특히 아프다. **회수는 `hold_id`·`held_by`·`held_at`을 모두 지우므로 "누구의 홀드가 언제 왜 회수됐는지"가 사라진다.** 사용자가 "좌석이 갑자기 없어졌다"고 문의하면 재구성할 방법이 없다.

### 규칙 35 메트릭 — 미구현

회수 건수, 후보 수 대비 회수율(stale 비율), 스윕 소요 시간이 없다. **stale 비율은 경합 강도의 직접 지표**라 운영에서 가장 보고 싶은 값인데 관측 수단이 없다.

### ★ `hold_id`가 NULL인 HELD/PAYING 행 — 탐지 수단 없음

후보 조회는 `hold_id IS NOT NULL`을 요구한다. 회수 UPDATE가 좌석과 홀드 소유권을 `(id, hold_id)` 쌍으로 검증하므로, `hold_id`가 없으면 검증할 대상 자체가 없기 때문이다. 소유권 정보 없이 임의로 `AVAILABLE`로 되돌리지 않기 위한 안전 조치다.

**그런 행은 정상 상태가 아니다.** `HELD`/`PAYING`인데 `hold_id`가 NULL이면 그 자체로 **정합성 위반**이며, 도메인의 `SeatSnapshot`이 복원 시점에 거부하는 조합이기도 하다.

문제는 **스위퍼가 손대지 않으므로 그런 행이 영구히 회수되지 않고 남는다**는 것이다. 제외는 안전을 위한 선택이지 정상 처리가 아니다.

| 항목 | 현재 상태 |
|---|---|
| DB `CHECK` 제약 | `status` 값 자체만 검사한다. **상태와 `hold_id`의 조합은 강제하지 않는다** |
| 탐지 | **없음.** 감사 로그도 메트릭도 미구현이라 이런 행이 생겨도 알 방법이 없다 |
| 알림 | **없음** |

향후 정합성 검사 쿼리, 메트릭, 또는 알림으로 탐지해야 한다. 상태-필드 조합 `CHECK` 제약을 추가하는 것도 선택지지만, **이번 Task에서 성급히 추가하지 않았다** — 기존 행에 미치는 영향과 다른 전이 경로와의 상호작용을 함께 검토해야 하고, 적용된 마이그레이션과 별개의 판단이 필요하다.

> 위 표의 "탐지"와 "알림"은 **실제로 구현되지 않았다.** 이 문서는 필요성을 기록할 뿐이며 어떤 형태로도 동작하고 있지 않다.

### 그 밖

| 항목 | 상태 |
|---|---|
| I-15 결제 승인 검증 | 미구현. `payment` 테이블·PG 연동 없음 |
| 멱등성 키 | 미구현 |
| REST API / 앱 배선 / 포트 인터페이스 | 미구현 |
| 운영 DataSource `innodb_lock_wait_timeout` | 미설정. 테스트 픽스처에만 적용됨 |

### 스키마 주석 — 정정 불가

`V1__seat_inventory.sql`의 `idx_seat_inventory_sweep` 주석은 스위퍼를 "TASK-2 후속"으로 설명한다. **이미 main에 병합되어 적용된 마이그레이션이므로 수정하지 않았다** — 내용을 고치면 Flyway checksum이 바뀌어 기존 환경의 마이그레이션 검증이 실패한다.

다만 그 주석이 지시한 설계("후보 SELECT 후 id 정렬하여 UPDATE 2단계")는 이번 구현이 그대로 따랐다. 실제 구현 상태는 이 문서가 기준이다.
