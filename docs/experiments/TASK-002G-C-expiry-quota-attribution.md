# 실험 — 만료 배치의 사용자별 quota 귀속 (Task 2G-C)

> TASK-002G-C · 2026-08-26
> 관련: [INVARIANTS.md](../INVARIANTS.md) I-10·I-11·I-12, [CLAUDE.md](../../CLAUDE.md) 규칙 1·2·8·11·21·26·30
> 선행: [2G-A](TASK-002G-user-hold-quota-race.md) · [2G-B](TASK-002G-B-quota-lock-order.md) · [2D](TASK-002D-seat-expiry-sweeper.md)

## 1. 문제 정의

만료 스위퍼는 **여러 사용자의 좌석을 한 벌크 UPDATE 로** 회수한다. 그런데 I-12 를 지키려면
회수된 좌석 수만큼 **각 사용자의** quota 를 줄여야 한다.

2G-A 는 이것을 "`held_by` 가 없어서 안 된다" 고 적었고, 이후 "`held_by` 를 넣어도 부족하다" 로
수정했다. **이번 Task 는 그 불충분함을 테스트로 증명하고 해결 후보를 검증한다.**

이번 단계도 **설계 검증 실험**이다. 운영 코드는 한 줄도 바꾸지 않았다.

## 2. 현재 계약 — 코드로 확인한 사실

| 항목 | 사실 |
|---|---|
| `ExpiryCandidate` | `record ExpiryCandidate(SeatId seatId, HoldId holdId)` — **`held_by` 없음** |
| `expire(candidates)` | `int` — **전체 `affected_rows` 하나**. 사용자별 결과 없음 |
| 부분 stale 의미 | `(id, hold_id) IN (...) AND status IN ('HELD','PAYING') AND expires_at <= NOW(3)` — stale 후보는 **건너뛰고 전체 롤백하지 않는다** |
| 후보 SELECT | `FOR UPDATE` 없음 — **비잠금**. 결과는 스냅샷이다 |
| `seat_inventory.held_by` | `BIGINT NULL` 로 존재. 다만 **quota scope 운영 계약은 미확정** (2G-A §9) |
| `UPDATE ... RETURNING` | MySQL 8.4 **미지원** |
| 회수 후 재조회 | `expireSql` 이 `hold_id = NULL, held_by = NULL` 로 **지운다** → 소유자 흔적이 남지 않는다 |

마지막 두 줄이 "회수된 행을 나중에 되짚어 귀속한다" 는 경로를 막는다.

## 3. ★ 두 사용자 ambiguity 의 결정적 재현

### 설계

같은 후보 구성에서 **stale 이 어느 사용자 쪽에 생기는지만** 바꾼 두 시나리오를 만든다.

- 사용자 A: 만료 후보 **3개**
- 사용자 B: 만료 후보 **2개**
- 후보 SELECT 시점 총 **5개**

| | 시나리오 1 | 시나리오 2 |
|---|---|---|
| SELECT 이후 stale 처리 | **A 의 후보 1개** | **B 의 후보 1개** |
| `expire()` 전체 반환값 | 4 | 4 |
| **올바른 사용자별 감소량** | **A=2, B=2** | **A=3, B=1** |

stale 은 운영 저장소의 실제 조건부 UPDATE 로 만든다 — `HELD → PAYING → SOLD`
(`startPayment` → `confirm`). 확정된 좌석은 `status IN ('HELD','PAYING')` 에 걸리지 않아
회수되지 않는다 (I-11). 픽스처는 `expires_at` 만 조정하고 상태 전이를 우회하지 않는다.
`Thread.sleep` 은 쓰지 않는다.

### 관측 결과 (3회 반복, 모두 동일)

```
[Task 2G-C] 시나리오1 view=SweeperView[candidatesForA=3, candidatesForB=2, totalAffected=4]
                     truth=Truth[expiredForA=2, expiredForB=2]
[Task 2G-C] 시나리오2 view=SweeperView[candidatesForA=3, candidatesForB=2, totalAffected=4]
                     truth=Truth[expiredForA=3, expiredForB=1]
```

`SweeperView` 는 **스위퍼가 실제로 볼 수 있는 것 전부**다 — 후보 시점의 사용자별 후보 수와
`expire()` 의 전체 반환값. 두 시나리오에서 **완전히 동일**하다.
`Truth` 는 DB 를 직접 들여다봐야만 알 수 있는 정답이며 **서로 다르다.**

> 같은 관측에서 두 정답이 나올 수 없다. 따라서 **그 관측만으로는 귀속 함수가 존재하지 않는다.**
> 이것은 구현 미비가 아니라 **정보가 없는 것**이다.

### `held_by` 를 후보에 넣어도 해결되지 않는 이유

`candidatesForA=3, candidatesForB=2` 가 곧 "후보에 `held_by` 를 넣었을 때 얻는 값" 이다.
두 시나리오에서 그 값도, 전체 반환값도 같다.

**`held_by` 는 후보 시점의 소유자일 뿐이다.** 어느 후보가 실제로 갱신됐는지는 여전히 알 수 없다.
필요한 것은 소유자 정보가 아니라 **실제로 변경된 행이 누구 것인지**다.

### 회수 후 재조회도 불가능하다

테스트로 확인했다 — 회수된 좌석은 `hold_id`, `held_by` 가 모두 `NULL` 이다.
갱신 후에 되짚을 단서가 남지 않는다.

## 4. 비교한 대안

현재 코드·잠금 순서(2G-B)·부분 stale 의미(2D)를 기준으로 비교했다.

| # | 대안 | 사용자별 귀속 | SQL/트랜잭션 비용 | 부분 stale 의미 | 판단 |
|---|---|---|---|---|---|
| 1 | **단일 벌크 UPDATE 유지** | **불가능** (§3) | UPDATE 1회 — 가장 쌈 | 유지 | ❌ I-12 와 결합 불가 |
| 2 | **(scope, user) 그룹별 조건부 UPDATE** | 각 그룹의 `affected_rows` 가 곧 정답 | UPDATE 가 **사용자 수만큼** 늘어남 | 유지 (조건 그대로) | **✅ 채택** |
| 3 | **모든 quota 행 선행 잠금 후 사용자별 UPDATE** | 가능 | 2 + quota 행 수 | 유지 | ✅ 2와 결합해 채택 |
| 4 | **사용자별 독립 트랜잭션** | 가능 | 트랜잭션·왕복 최다 | 유지 | 보류 — §7 |
| 5 | **UPDATE 전 잠금 조회 / UPDATE 후 재조회** | **후자는 불가능** (`held_by` 제거됨) | 잠금 보유 시간 증가 | 유지 | ❌ 재조회 불가, 선행 잠금은 3에 흡수 |

2·3 은 배타적이지 않다. **3의 잠금 순서 위에 2의 그룹 UPDATE 를 얹는 것**이 이번에 검증한 후보다.

4 는 배치 전체 원자성을 포기하는 대신 한 사용자의 실패가 다른 사용자를 막지 않게 한다.
**어느 쪽이 맞는지는 운영 정책 결정이라 이번에 확정하지 않았다** (§10).

## 5. 선택한 테스트 전용 해결 후보

`Task2gExpiryQuotaCoordinator` — **테스트 소스에만** 있고 운영 `JdbcSeatExpiryRepository` 를
**그대로 재사용**한다. 바뀐 것은 호출 방식뿐이다.

```
(1) 후보 조회 — 테스트 전용 SELECT 에 held_by 추가 (운영 SQL 은 그대로)
(2) (quotaScopeId, userId) 로 그룹화, 그룹은 오름차순 · 그룹 안 좌석은 seatId 오름차순
(3) quota 행을 (scopeId, userId) 오름차순으로 전부 먼저 잠금        ← quota → seat (2G-B)
(4) 그룹마다 expiryRepository.expire(groupCandidates) 호출
(5) 그 그룹의 affected_rows 만큼만 quota 감소
    - affected_rows == 0 이면 감소 SQL 자체를 보내지 않는다
    - 감소가 거부되면 예외 → 트랜잭션 전체 롤백
```

**후보 수가 아니라 실제 `affected_rows` 를 쓴다** (2G-A §7 의 원칙).

### 트랜잭션 경계 — 세 구간을 분리한다

| 구간 | 경계 | 내용 |
|---|---|---|
| **후보 탐색** | 정산 트랜잭션 **밖**, 비잠금 | `groupCandidates(...)` |
| **경쟁 전이** | 정산 트랜잭션 **밖**, 별도 트랜잭션에서 **커밋** | 테스트 훅 (`afterCandidateSelect`) |
| **정산** | **하나의 트랜잭션** | quota 잠금 → 좌석 회수 → quota 감소 |

**훅을 정산 트랜잭션 안에서 돌리면 안 된다.** 같은 `DataSource` 를 쓰는 `confirm` 이 그
트랜잭션에 참여해 **seat 를 먼저 잠그고 quota 를 나중에 잠그는 역순**이 되고, 정산이 실패할 때
그 전이까지 함께 롤백된다. 그러면 "다른 요청이 먼저 확정했다" 는 상황 자체가 재현되지 않는다.
초안이 그 구조였고, 이번에 분리했다.

`settleWithin(...)` 은 호출자가 연 트랜잭션에 참여하는 별도 API 다. **post-select 경쟁 훅과
합치지 않았다** — 두 API 의 목적이 다르다.

#### 두 계약은 런타임 guard 로 강제된다

`TransactionTemplate` 의 기본 전파 속성은 `PROPAGATION_REQUIRED` 다. 그래서 `sweepAndSettle` 을
외부 트랜잭션 안에서 부르면 `topLevel` 이 새 트랜잭션을 열지 않고 **조용히 그 트랜잭션에 참여**한다.
반대로 `settleWithin` 을 트랜잭션 없이 부르면 `SELECT ... FOR UPDATE` 잠금이 문장 종료와 함께 풀리고
좌석 회수와 quota 감소가 **각각 autocommit** 된다.

이 전제가 초안에서는 **메서드 이름과 문서에만** 있었다. 이제 런타임에서 강제한다.

| API | 진입 조건 | 위반 시 |
|---|---|---|
| `sweepAndSettle` | 활성 트랜잭션이 **없어야** 함 | `IllegalStateException` — 메시지에 `settleWithin` 사용 안내 |
| `settleWithin` | 활성 트랜잭션이 **있어야** 함 | `IllegalStateException` — 메시지에 `sweepAndSettle` 사용 안내 |

**두 검사 모두 후보 조회와 DB 변경보다 먼저** 수행된다. 잘못된 호출은 quota 잠금은커녕
SELECT 도 실행하지 못하고, `sweepAndSettle` 의 경우 **경쟁 전이 콜백도 실행되지 않는다.**

`REQUIRES_NEW` 로 억지로 떼어내지 않았다 — 그러면 정산이 호출자 롤백의 영향을 벗어난다.
**잘못된 호출 자체를 거부하는 편이 계약이 단순하다.**

이 guard 덕분에 `confirmInSeparateTransaction` 은 기본 `PROPAGATION_REQUIRED` 로도
독립 최상위 트랜잭션이 된다 — 훅이 실행되는 시점에 활성 스위퍼 트랜잭션이 없기 때문이다.

### quota → seat 잠금 순서 — 검증한 범위

만료 정산 경로가 quota 행을 `(scopeId, userId)` 오름차순으로 먼저 잠그고, 그룹 안에서는
좌석을 `seatId` 오름차순으로 처리한다. **그 결정적 순서를 코드와 관측값으로 확인했다.**

> **전체 시스템이 deadlock-free 라는 뜻이 아니다.** 확정 경로나 다중 스위퍼와의 실제 교착은
> 검증하지 않았고, 데드락 재시도 정책도 아직 없다.

### 부분 stale 의미

바뀌지 않았다. 그룹 UPDATE 의 조건이 운영 SQL 그대로이므로 stale 후보는 건너뛰어지고
같은 그룹의 유효한 후보는 회수된다. **한 사용자의 stale 이 다른 사용자의 회수를 막지 않는다.**

### `held_by` 가 NULL 인 후보 — 조용히 제외하지 않는다

후보 SQL 은 운영과 **같은 대상 집합**을 조회하고 `held_by` 컬럼만 더한다.
`held_by IS NOT NULL` 필터를 **붙이지 않는다.** 붙이면 소유자가 없는 만료 후보가 조용히
제외되고, 그 좌석은 영원히 회수되지 않으면서 아무도 그 사실을 모른다.

`status IN ('HELD','PAYING')` 과 `held_by` 의 결합을 강제하는 **DB CHECK 가 없으므로**
그런 행이 생길 가능성을 구조적으로 배제할 수 없다. 그래서 **탐지 대상**으로 둔다.

- `rs.getObject("held_by", Long.class)` 로 읽는다 — `getLong` 은 NULL 을 **0 으로** 돌려주므로
  존재하지 않는 사용자 0 그룹이 생기고 좌석이 조용히 회수된다
- NULL 이면 `QuotaDriftException` 을 던지고 **좌석을 회수하지 않는다**
- 메시지에 seat ID 와 `held_by` 누락 사실을 담는다
- 후보 탐색 단계에서 터지므로 **정산 트랜잭션 자체가 시작되지 않는다**

### quota 행이 없을 때 — 조용히 무시하지 않는다

좌석은 그 사용자 것인데 카운터 행이 없다면 **이미 어긋난 상태**다.
넘어가면 그 사용자의 카운터가 영구히 실제와 달라진다.
그래서 **예외를 던지고 배치를 중단**하도록 했다. 운영에서 이것이 맞는 선택인지는 §10 의 결정 사항이다 —
배치 전체를 멈추는 것과 그 사용자만 건너뛰고 알람을 올리는 것 사이의 트레이드오프가 있다.

## 6. 검증 결과

`UserHoldQuotaExpiryAttributionTest` — 실제 MySQL 8.4 Testcontainers, **23 tests**.

### §1 RED — 귀속 불가능성 (3)

| 검증 | 결과 |
|---|---|
| 같은 요약·같은 반환값이 서로 다른 정답을 갖는다 | 통과 (`view` 동일, `truth` 상이) |
| 후보에 `held_by` 를 넣어도 해결되지 않는다 | 통과 |
| 회수 후 재조회로도 귀속할 수 없다 (`hold_id`·`held_by` NULL) | 통과 |

> §1 이 통과한다는 것은 **귀속 불가능성을 관측했다**는 뜻이지 올바른 동작이라는 뜻이 아니다 (규칙 27).

### §2 GREEN — SELECT 이후 stale 이 나도 사용자별 실제 회수 수를 얻는다 (10)

**모든 stale 은 후보 SELECT 이후에, 별도 트랜잭션에서 커밋된다.**

| 검증 | 후보 수 | 실제 회수 | 결과 |
|---|---|---|---|
| SELECT 이후 A 하나가 stale | A=3, B=2 | A=2, B=2 | 통과 |
| SELECT 이후 B 하나가 stale | A=3, B=2 | A=3, B=1 | 통과 |
| 같은 그룹의 나머지 후보는 회수된다 | | | 통과 |
| 한 사용자의 stale 이 다른 사용자의 회수를 막지 않는다 | | | 통과 |
| A 후보 전체가 stale → A 는 0, 감소 SQL 미발송 | A=3 | A=0, B=2 | 통과 |
| stale 사용자의 quota 를 과도하게 감소시키지 않는다 | B=2 | B=1 | 통과 |
| 사용자별 감소량 합계 == 실제 전체 회수 수 | | | 통과 |
| 후보가 없는 사용자는 배치에 포함되지 않는다 (SELECT **이전** stale) | | | 통과 |
| quota 잠금이 `(scopeId, userId)` 오름차순 | | | 통과 |
| 그룹 안 좌석이 `seatId` 오름차순 | | | 통과 |

**앞의 두 줄이 이 Task 의 핵심이다.** 후보 수는 같고 stale 위치만 다른데 사용자별 감소량이
정확히 갈린다 — §3 이 불가능하다고 보인 바로 그 구분이다.

> **quota 수치에 대한 제한.** `confirm` 경로의 quota 감소는 **아직 운영에 없다.**
> 그래서 확정된 좌석 몫은 카운터에 남는다. 이 절이 검증하는 것은 오직
> **만료 경로가 줄여야 할 사용자별 delta** 와 그것이 사용자별 실제 `affected_rows` 와
> 일치하는지다. 확정분에 해당하는 감소는 **confirm 경로의 후속 과제**다.
> 그래서 "최종 quota == 전체 활성 좌석 수" 를 단언하지 않는다. **I-12 는 미완결이다.**

### §3 트랜잭션 경계와 실패 계약 (6)

| 검증 | 결과 |
|---|---|
| quota 감소가 거부되면 좌석 회수도 롤백 (다른 사용자 것까지) | 통과 |
| 외부 트랜잭션 롤백 시 좌석·quota 함께 복구 (`settleWithin`) | 통과 |
| quota 행이 없으면 조용히 무시하지 않고 실패 | 통과 |
| **스위퍼 롤백이 독립 커밋된 `confirm` 을 되돌리지 않는다** | 통과 |
| **`settleWithin` 은 활성 트랜잭션이 없으면 거부** (quota 잠금 전, 좌석·quota 불변) | 통과 |
| **`sweepAndSettle` 은 외부 트랜잭션 안에서 호출 불가** (콜백도 실행 안 됨) | 통과 |

마지막 줄이 경계 분리의 회귀 테스트다. 훅이 정산 트랜잭션 안에서 돌던 초안 구현에서는
이 테스트가 **실패한다** (확정 좌석이 `SOLD` 가 아니라 `HELD` 로 되돌아간다).

### §4 `held_by` NULL drift 탐지 (4)

| 검증 | 결과 |
|---|---|
| 조용히 제외하지 않고 명시적으로 실패 (메시지에 seat ID 포함) | 통과 |
| 해당 좌석은 회수되지 않는다 | 통과 |
| quota 는 변경되지 않는다 | 통과 |
| 다른 사용자의 좌석도 정산 트랜잭션 시작 전에 그대로 유지된다 | 통과 |

초안처럼 `held_by IS NOT NULL` 로 걸러내면 이 네 개가 모두 **실패한다** (예외가 나지 않는다).

### RED 확인

수정한 테스트를 **초안 구현에 되돌려 실행**해 정확히 실패하는 것을 확인했다.

| 보완 | 초안에서 실패한 테스트 |
|---|---|
| 경계 분리 · `held_by` NULL 탐지 | 5개 — `스위퍼_롤백은_독립_커밋된_confirm_을_되돌리지_않는다` + §4 의 네 개 |
| 트랜잭션 진입 guard | 2개 — `settleWithin_은_활성_트랜잭션이_없으면_거부한다`, `sweepAndSettle_은_외부_트랜잭션_안에서_호출할_수_없다` |

## 7. SQL 및 트랜잭션 수 증가 비용

| | 현재 (단일 벌크) | 채택 후보 (그룹별) |
|---|---|---|
| 후보 SELECT | 1 | 1 |
| quota 행 잠금 | 0 | **사용자 수** |
| 좌석 UPDATE | 1 | **사용자 수** |
| quota 감소 | 0 | 실제 회수 > 0 인 사용자 수 |
| 트랜잭션 | 1 | 1 (사용자별 분리 시 사용자 수) |

배치 크기 500 에 사용자가 200명이면 UPDATE 가 1회에서 200회가 된다.
**이 비용은 측정하지 않았다.** 배치 크기·사용자 분포·잠금 보유 시간에 달려 있고,
`innodb_lock_wait_timeout = 3` (규칙 9) 아래에서 사용자 요청 경로와의 경합에 어떤 영향을 주는지는
별도 측정이 필요하다.

## 8. 운영 코드에 아직 반영하지 않은 이유

1. **quota scope 가 미확정이다** (2G-A §9). `event_id` 인지 `schedule_id` 인지 정해지지 않았고,
   그 결정이 후보 그룹화 키를 바꾼다.
   *(→ [TASK-002G-D](TASK-002G-D-quota-scope-contract.md) 에서 판매 이벤트 단위로 결정됐다.
   이 항목은 당시의 미결정 상태를 기록한 역사적 설명이다.)*
2. **배치 원자성 정책이 미정이다.** 한 사용자의 실패가 배치 전체를 롤백해야 하는지,
   그 사용자만 건너뛰고 알람을 올려야 하는지 정해지지 않았다 (§5, §10).
3. **비용을 측정하지 않았다** (§7). UPDATE 수 증가가 감당 가능한지 모른 채 계약을 굳힐 수 없다.
4. **`ExpiryCandidate` 는 운영 계약이다.** 여기에 `held_by` 를 넣을지, 아니면 반환 타입을
   바꿀지는 위 세 가지가 정해진 뒤의 결정이다.
5. 운영 마이그레이션은 "적용됨, 수정 금지" 로 다루는 되돌리기 어려운 결정이다.

## 9. 검증된 것과 아직 검증하지 않은 것

### 검증된 것

- 전체 `affected_rows` 만으로는 사용자별 귀속이 **불가능하다** — 같은 관측에서 두 정답
- 후보에 `held_by` 를 넣어도 부족하다
- 회수 후 재조회로도 귀속할 수 없다 (`hold_id`·`held_by` 제거됨)
- **(scope, user) 그룹별 `expire()` 호출은 사용자별 실제 회수 수를 정확히 준다** —
  stale 이 **후보 SELECT 이후 별도 트랜잭션에서 커밋**되는 상황에서 검증했다
- **스위퍼 정산이 롤백돼도 독립 커밋된 경쟁 전이는 유지된다**
- **`held_by` 가 NULL 인 만료 후보를 조용히 제외하지 않고 drift 로 탐지한다**
- **두 API 의 트랜잭션 진입 조건이 런타임 guard 로 강제된다** — 잘못된 호출은 후보 조회와
  DB 변경 전에 실패하고, `sweepAndSettle` 의 경쟁 전이 콜백도 실행되지 않는다
- 후보 수가 아니라 실제 `affected_rows` 로 감소하면 stale 사용자를 과대 감소하지 않는다
- 실제 회수 0 이면 감소 SQL 을 보내지 않는다
- quota 행 잠금이 `(scopeId, userId)` 오름차순, 그룹 안은 `seatId` 오름차순
- 부분 stale 의미가 유지된다
- quota 감소 거부·외부 롤백 시 좌석과 quota 가 함께 복구된다
- quota 행 부재를 조용히 무시하지 않는다

### 아직 검증하지 않은 것

- **SQL·트랜잭션 증가 비용** (§7) — 전혀 측정하지 않았다
- **다중 스위퍼 인스턴스** — 두 스위퍼가 같은 후보를 동시에 잡을 때의 동작. 후보 SELECT 가
  비잠금이라 겹칠 수 있고, 조건부 UPDATE 가 이중 회수는 막지만 **quota 이중 감소 여부는 확인하지 않았다**
- **스위퍼 ↔ 사용자 요청 경로의 교착** — 2G-B 는 선점·해제만 다뤘다
- **전체 deadlock-free** — 검증하지 않았다. 이번에 확인한 것은 **만료 정산 경로가 quota → seat
  순서를 적용한다**는 것과 그 처리 순서가 결정적이라는 것뿐이다
- **`confirm` 경로의 quota 감소** — 운영에 없다. 이번 실험 범위 밖이며 후속 과제다
- **데드락 재시도 정책** — 정해지지 않았다
- **배치 크기와 사용자 분포에 따른 잠금 보유 시간**
- **사용자별 트랜잭션 분리(대안 4)** — 구현·측정하지 않았다
- **drift 탐지·복구** — 정합성 검사 쿼리가 없다

> 반복 실행 결과는 보조 근거다 (규칙 30). 핵심 근거는 §3 의 결정적 재현과 §5 의 구조적 논증이다.

## 10. Task 2G-D 에서 결정해야 할 운영 계약

1. **quota scope** — `event_id` vs `schedule_id`. event 모델 도입 여부를 포함한 정책 결정
2. **`ExpiryCandidate` 확장 vs 반환 타입 변경** — 그룹화를 저장소가 할지 호출자가 할지
3. **배치 원자성** — 한 사용자의 실패가 배치 전체를 롤백할지, 건너뛰고 알람만 올릴지
4. **quota 행 부재의 처리** — 중단 vs 건너뛰기 + drift 알람
5. **사용자별 트랜잭션 분리 여부** — 원자성과 처리량의 트레이드오프
6. **데드락 재시도 정책** — 횟수·백오프. 스위퍼는 배치라 사용자 요청과 다른 정책이 가능하다
7. **다중 스위퍼 허용 여부** — 단일 인스턴스 강제(ShedLock)로 문제를 없앨지
8. **`held_by` NULL 행의 처리** — DB CHECK 로 막을지, 탐지 후 배치 중단할지, 건너뛰고 알람만 올릴지
9. **drift 탐지 쿼리와 보정 절차**

## 11. 남은 위험

| 항목 | 내용 |
|---|---|
| **다중 스위퍼 인스턴스** | 후보 SELECT 가 비잠금이라 두 스위퍼가 같은 후보를 잡을 수 있다. 조건부 UPDATE 가 좌석 이중 회수는 막지만 **quota 이중 감소는 확인하지 않았다.** 그룹별 UPDATE 로 나뉘면 각 그룹의 `affected_rows` 는 실제 변경분이므로 구조적으로는 안전해 보이나 **관측하지 않았다** |
| **SQL 수 증가** | 사용자 수만큼 UPDATE 가 늘어난다. 미측정 |
| **quota 행 부재 처리** | 현재 후보 구현은 배치를 중단시킨다. 한 사용자의 drift 가 전체 만료를 막는다 — 운영에서 맞는지 미결정 |
| **배치 전체 롤백** | 한 사용자의 quota 감소 실패가 다른 사용자의 좌석 회수까지 되돌린다. I-10(만료 회수)이 지연된다 |
| **데드락 재시도 미정** | 스위퍼는 배치라 재시도가 자연스럽지만 정책이 없다 |
| **quota scope 미확정** | 그룹화 키가 바뀌면 이 실험의 그룹 경계도 바뀐다 |
| **drift 탐지·복구 없음** | `held_seats` 와 실제 활성 좌석을 대조하는 쿼리가 없다 |
| **`confirm` 경로 quota 감소 부재** | 확정된 좌석 몫이 카운터에 남는다. 만료 경로만으로는 `held_seats` 가 실제 활성 좌석과 일치하지 않는다 — 이번 실험이 그것을 단언하지 않는 이유다 |
| **`held_by` NULL 행의 발생 원인 미상** | 탐지는 하지만 왜 생기는지는 조사하지 않았다. DB CHECK 로 막을지, 발생 경로를 찾을지 미결정 |
| **drift 탐지 시 배치 중단** | 한 좌석의 `held_by` NULL 이 전체 만료를 막는다. 운영에서 맞는지 미결정 |
| **I-12 는 여전히 미구현** | 운영 테이블·저장소·서비스가 없다. 이 실험은 설계 검증이다 |
