## 1. 목적과 범위

사용자가 직접 홀드를 푸는 경로를 저장소 수준에서 구현한다. Task 2D 문서에서 "도메인 전이는 있으나 인프라 경로가 없다"고 기록한 항목이다.

**해제의 단위는 좌석이 아니라 홀드다.** 사용자는 "12A를 놓겠다"가 아니라 **"내가 잡은 것을 놓겠다"** 고 요청하며, 그 홀드에 묶인 1~4석이 함께 풀린다. 좌석 단위로 노출하면 다좌석 홀드의 일부만 풀린 어중간한 상태가 생긴다.

> **범위 주의.** 이번 Task는 **저장소 수준**이다. REST API와 멱등키 저장소가 없으므로 **FR-2.5가 완성된 것이 아니다.** §8에 남은 범위를 기록한다.

### 계약을 API 가시성으로 강제한다

```java
public  int          releaseAll(HoldId, UserId)              // 유일한 외부 진입점
        List<SeatId> findReleasableSeats(HoldId, UserId)     // package-private
        int          release(HoldId, UserId, List<SeatId>)   // package-private
```

후보 조회와 조건부 UPDATE는 **내부 협력 단계**다. 공개하면 호출자가 후보를 임의로 골라 넘길 수 있고, 그러면 **홀드의 일부만 해제된 상태**가 만들어진다. "해제의 단위는 홀드"라는 계약을 문서가 아니라 가시성으로 지킨다.

테스트는 같은 패키지라 두 메서드에 접근할 수 있다. **테스트를 위해 `public`으로 올리거나 우회 메서드를 만들지 않았다.**

## 2. 순진한 구현의 실패 — 대상 기준 해제

```sql
-- 테스트 전용 NaiveSeatReleaseRepository
UPDATE seat_inventory SET status='AVAILABLE', ... WHERE id IN (...)
```

홀드 소유권도, 요청자도, 현재 상태도 확인하지 않는다. CLAUDE.md 규칙 18이 금지하는 형태다.

**왜 실제 장애에서 가능한가.** 해제 요청은 네트워크를 타고 오며 **응답은 유실될 수 있다.** 사용자가 재시도할 무렵 그 좌석은 이미 만료되어 다른 사람이 잡았거나, 결제를 마쳐 팔렸을 수 있다. 좌석 기준 해제는 그 상황을 구분하지 못한다.

**스레드가 필요 없다.** 결함이 타이밍이 아니라 "해제를 좌석 기준으로 하면 그 좌석의 현재 주인이 누구든 풀린다"는 사실 자체이기 때문이다.

| 시나리오 | 좌석 기준 해제 | 홀드 기준 CAS |
|---|---|---|
| 그 사이 **남이 다시 잡음** | **1건 — 남의 홀드 파괴** ❌ | **0건**, 새 홀드 유지 ✅ |
| 그 사이 **확정됨** | **1건 — 판 좌석이 풀리고 `reservation_id`까지 삭제** ❌ | **0건**, `SOLD` 유지 ✅ |

두 경우 모두 오류 로그는 한 줄도 남지 않는다. UPDATE가 정상 성공하기 때문이다.

## 3. 홀드 단위 해제와 자연 멱등

### 최종 CAS

```sql
UPDATE seat_inventory FORCE INDEX (PRIMARY)
   SET status='AVAILABLE', hold_id=NULL, held_by=NULL, held_at=NULL,
       expires_at=NULL, reservation_id=NULL, version=version+1
 WHERE hold_id = ?
   AND held_by = ?
   AND id      IN (?, ?, ...)
   AND status  IN ('HELD','PAYING')
```

| 조건 | 막는 것 |
|---|---|
| `hold_id` | 그 사이 회수되고 **남이 새로 잡은** 좌석 |
| `held_by` | **요청자가 아닌 사람**의 해제 시도 |
| `id IN (...)` | 잠금 순서를 PK로 고정 |
| `status IN ('HELD','PAYING')` | **확정된 좌석** |

`held_by`는 `hold_id`에 더한 두 번째 소유권 검증이다. `hold_id`만으로도 충분해 보이지만, 홀드 식별자가 로그·URL 등으로 노출됐을 때 요청자 확인이 남는다.

### 만료 스위퍼와 다른 점

Task 2D의 회수는 `(id, hold_id)` **행 생성자 쌍**을 썼다. 후보마다 서로 다른 홀드를 가질 수 있어 교차 매칭을 막아야 했기 때문이다.

**해제는 그럴 필요가 없다.** 한 홀드의 좌석은 모두 같은 `hold_id`를 가지므로 스칼라 조건 하나가 모든 좌석에 동일하게 적용된다.

### 자연 멱등 (규칙 18)

같은 요청을 반복하면 두 번째부터 조건이 불일치해 0건이 된다.

측정: 3회 연속 호출 → `2건, 0건, 0건`. `version`은 첫 호출에서만 증가하고 이후 그대로다. 예외는 발생하지 않는다. **멱등키 인프라 없이 저장소 CAS만으로 성립하는 성질이다.**

#### 0건의 의미를 과장하지 않는다

0건은 **"현재 요청 조건에 맞는 해제 가능한 활성 좌석이 없다"** 는 사실 하나이며, **자연 멱등 계약상 성공 no-op으로 처리한다.**

원인은 여럿이고 **구분되지 않는다.**

| 가능한 원인 |
|---|
| 이미 해제됨 |
| 존재하지 않는 `HoldId` |
| 다른 사용자의 홀드 |
| 이미 `SOLD` |
| 그 밖에 `hold_id`·`held_by`·`status` 조건에 맞는 활성 좌석이 없음 |

따라서 **0건이 좌석의 현재 상태가 `AVAILABLE`임을 증명하지 않고, 요청자가 정당한 소유자임을 뜻하지도 않는다.** 앱이 204로 응답하는 것은 멱등 계약이지 상태나 인증에 대한 단언이 아니다.

향후 I-12 quota 감소도 **실제 `affected_rows`가 0이면 수행하지 않는다.** 요청 좌석 수가 아니라 실제 변경된 행 수만큼만 줄인다.

## 4. 후보 조회와 최종 CAS의 분리

홀드로 좌석을 찾는 조건(`hold_id`, `held_by`)과 잠금 순서를 정하는 기준(PK)이 다르다. 홀드 인덱스 순서로 곧장 잠그면 확정·만료 경로(PK 순서)와 교차해 데드락이 날 수 있다(규칙 2).

후보는 **조회 시점의 스냅샷일 뿐** 현재 상태의 진실이 아니다. 그 사이 확정·만료·재선점이 일어날 수 있으므로 최종 UPDATE가 모든 조건을 다시 검사한다.

### 전부-또는-전무가 아니다

다좌석 선점(I-9)과 **반대**다. 후보 하나가 stale하다고 나머지를 롤백하면 사용자는 아무것도 놓지 못한 채 남는다. 유효한 좌석은 해제하고 stale한 좌석은 `affected_rows`에서 빠진다.

측정: 3석 홀드에서 후보 조회 후 1석이 확정된 상태로 해제 → **2건 해제, 확정된 1석은 `SOLD` 유지.**

### 인덱스 — V3로 `(hold_id)` 추가

기존 `(held_by, status)`로도 답은 나온다. 그러나 **그 인덱스는 대상 사용자의 활성 좌석을 전부 스캔한 뒤 `hold_id`로 걸러낸다.** 비용이 `O(홀드 좌석 수)`가 아니라 `O(사용자 활성 좌석 수)`다.

**사용자별 활성 좌석의 상한은 I-12가 강제할 값인데 아직 구현되지 않았다.** 따라서 "사용자별 활성 좌석은 항상 적다"를 전제로 삼을 수 없다.

#### 측정 데이터 분포

| 항목 | 값 |
|---|---|
| 전체 좌석 | 100,000 |
| 활성(`HELD`/`PAYING`) 행 | 20,000 |
| 전체 홀드 수 | 5,000 |
| 홀드당 좌석 | 4 |
| **불리 분포** — 사용자 1 | 활성 **2,000석**, 홀드 500개 (여러 스케줄에 걸침) |
| **일반 분포** — 그 외 사용자 | 활성 4석, 홀드 1개 |

두 측정의 **대상 홀드는 모두 4석**이다. 다른 것은 그 홀드를 가진 사용자의 활성 좌석 수뿐이므로, 차이는 전적으로 인덱스 탐색 범위에서 온다.

#### `EXPLAIN ANALYZE` 결과

각 3회 실행, 시간은 중앙값. `FORCE INDEX`로 비교 대상을 고정했다.

| 분포 | 인덱스 | 내부 스캔 행 | 반환 행 | filesort | 시간(보조) |
|---|---|---|---|---|---|
| 일반 (4석) | `(held_by, status)` | 4 | 4 | 없음 | 0.0345ms |
| 일반 (4석) | **`(hold_id)`** | 4 | 4 | 없음 | 0.0306ms |
| **불리 (2,000석)** | `(held_by, status)` | **2,000** | 4 | 없음 | 1.61ms |
| **불리 (2,000석)** | **`(hold_id)`** | **4** | 4 | 없음 | 0.027ms |

**판단 근거는 스캔 행 수와 데이터 증가 시의 복잡도다.** 실행 시간은 보조 수치로만 봤다 — 평균 시간 한 번으로 결론 내리면 일반 분포에서 차이가 거의 없어 잘못된 결론에 이른다.

`(hold_id)`는 스캔 행 수가 **홀드 좌석 수(≤4)에만 비례**하고 사용자 활성 좌석 수나 전체 행 수와 무관하다. V3 마이그레이션으로 추가했다. 기존 인덱스는 다른 경로의 영향까지 측정한 뒤 판단하기 위해 **삭제하지 않았다.**

#### 왜 키 컬럼이 `(hold_id)` 하나인가

- **InnoDB 보조 인덱스에는 PK인 `id`가 암묵적으로 포함된다.** 후보 조회가 읽는 값은 `id`뿐이므로 `id`를 키 컬럼으로 다시 적을 이유가 없다.
- **이 인덱스를 전체 쿼리의 covering index라고 부르면 안 된다.** 후보 조회는 `held_by`와 `status`도 검사하는데 이 인덱스는 그 두 컬럼을 갖지 않는다. 역할은 **후보 범위를 홀드 좌석 수로 제한하는 탐색**이며, `held_by`·`status`는 최종 소유권·상태 검증 조건이다.
- **잠금 순서도 이 인덱스에 의존하지 않는다.** 후보를 받은 뒤 Java에서 `id` 오름차순으로 정렬하고 `FORCE INDEX (PRIMARY)`로 갱신하는 것이 순서를 보장한다(규칙 2·3).

> 처음 측정은 사용자당 활성 좌석이 2석뿐인 데이터로 했다. 그 분포에서는 `(held_by, status)`가 자명하게 선택적이라 **인덱스가 불필요하다는 잘못된 결론**이 나왔다. 최악 분포를 포함하지 않은 측정은 근거가 되지 못한다.

`EXPLAIN` 테스트는 운영 SQL 상수를 그대로 사용한다(`FIND_SEATS_SQL`, `releaseSql(int)`). 회수 UPDATE는 `PRIMARY`, 후보 조회는 `idx_seat_inventory_hold`를 쓰며 filesort가 없다.

## 5. 확정 · 만료와의 경쟁

해제는 **세 번째 전이 주체**다. 지금까지 같은 행을 노리는 것은 확정과 만료 둘이었는데 여기에 사용자의 해제가 더해진다. 셋 다 `HELD`/`PAYING`을 출발점으로 한다.

### 결정적 순서 검증

| 순서 | 먼저 | 나중 | 최종 상태 | `version` 증가 |
|---|---|---|---|---|
| 해제 → 확정 | 해제 1건 | 확정 `NOT_CONFIRMED` | `AVAILABLE` | 1 |
| 확정 → 해제 | 확정 `CONFIRMED` | 해제 **0건** | `SOLD` | 1 |
| 해제 → 만료 | 해제 1건 | 만료 **0건** | `AVAILABLE` | 1 |
| 만료 → 해제 | 만료 1건 | 해제 **0건** | `AVAILABLE` | 1 |

`version` 증가가 1이라는 것이 **정확히 한 전이만 성공했다**는 뜻이다.

> **해제와 만료는 결과 상태가 같다**(둘 다 `AVAILABLE`). 그래서 어느 쪽이 이겼는지는 상태로 구분할 수 없고 `affected_rows`로만 알 수 있다. 확정과의 경쟁(`SOLD` vs `AVAILABLE`)과 다른 점이다.

### 동시 경합 (통계적 보조 결과)

`CountDownLatch` 동시 출발, `Thread.sleep` 미사용. 각 라운드마다 새 좌석을 만든다.

| 경합 | 라운드 | 승패 | 양쪽 성공·양쪽 실패 | `version` 위반 | 필드 조합 위반 | 오류/deadlock |
|---|---|---|---|---|---|---|
| 해제 vs 확정 | 150 | 해제 102 / 확정 48 | **0** | **0** | **0** | **0** |
| 해제 vs 만료 | 150 | 해제 83 / 만료 67 | **0** | **0** | **0** | **0** |

전체 실행 후 테이블 스캔: `SOLD` 필드 조합 위반 0행, `AVAILABLE` 잔여 필드 0행, 중간 상태로 남은 좌석 0행.

> **이 결과는 증명이 아니다.** 이 환경과 실행 횟수에서 관측되지 않았다는 **통계적 보조 근거**다(규칙 30). 구조적 논증은 §3의 CAS 조건, 결정적 재현은 위 순서 테스트다.

## 6. 외부 트랜잭션 참여 — 검증됨

Task 2D에서 **문서로만** 기록했던 "`JdbcTemplate`은 외부 트랜잭션에 참여한다"를 이번에 실제로 검증했다.

| 시나리오 | `releaseAll()` 반환 | 좌석 최종 상태 |
|---|---|---|
| 외부 트랜잭션 **롤백** | **2** (UPDATE 자체는 성공) | **`HELD` 유지** — 해제도 롤백됨 |
| 외부 트랜잭션 **커밋** | 2 | `AVAILABLE` — 반영됨 |

검증은 **공개 진입점인 `releaseAll(HoldId, UserId)`** 를 외부 트랜잭션 안에서 호출해 수행했다. 내부 협력 메서드를 직접 부르지 않았다.

**반환값과 실제 반영이 갈릴 수 있다는 점이 중요하다.** `releaseAll()`이 2를 돌려줘도 외부 트랜잭션이 롤백되면 아무것도 해제되지 않는다. 이 반환값을 quota 감소 등에 쓸 때, **감소도 같은 트랜잭션 안에 있어야** 일관성이 유지된다.

자체 `TransactionTemplate`은 만들지 않았다. 되돌릴 것이 없고, Task 2C식 rollback-only 전파 문제도 만들지 않는다. 향후 quota 감소와 묶는다면 **경계는 애플리케이션 서비스가 소유해야 한다.**

| `EXPLAIN` SELECT → `idx_seat_inventory_hold` (V3), filesort 없음 | 통과 |
| `releaseAll` 만 public, 나머지 package-private | 통과 (컴파일로 강제) |
| 경합 테스트가 예외를 수집·검증 | 통과 |
| 외부 트랜잭션 롤백/커밋 | 통과 |

### 한계

- **저장소 수준 검증이다.** 실제 사용자 요청 경로(HTTP → 인증 → 애플리케이션 서비스)는 없다.
- **`held_by` 검증은 호출자가 올바른 `UserId`를 넘긴다는 전제**에 의존한다. 그 값이 인증 주체와 일치하는지는 앱 계층의 책임이다.
- 동시성 결과는 로컬 Testcontainers 환경의 것이다.

### I-12를 구현하기 전에 결정할 것

이번 Task로 **quota 이탈 경로 세 가지가 모두 상태 전이 수준에서 갖춰졌다.**

| 경로 | 상태 전이 | quota 감소 연동 |
|---|---|---|
| `PAYING → SOLD` 확정 | 구현됨 (2B) | **미구현** |
| 만료 회수 | 구현됨 (2D) | **미구현** |
| 자발적 해제 | **구현됨 (2E)** | **미구현** |

남은 것은 `user_hold_quota` 테이블과 증감 연동이다. 구현 전에 결정해야 할 것:

1. **트랜잭션 경계를 누가 소유하는가.** 좌석 UPDATE와 quota 증감은 원자적으로 묶여야 한다. 그 순간 저장소들은 외부 트랜잭션에 참여하게 되고, Task 2C의 `JdbcMultiSeatHoldRepository`는 내부 `setRollbackOnly()`를 쓰므로 **`UnexpectedRollbackException` 위험이 있다.** 이 문제를 먼저 풀어야 한다. *(→ [TASK-002F](TASK-002F-transaction-boundary.md)에서 재현하고 해소했다. 위 서술은 TASK-002E 시점 기준으로 유지한다.)*

2. **부분 해제 시 감소량을 어떻게 정하는가.** 해제는 전부-또는-전무가 아니므로 `affected_rows`가 후보 수보다 적을 수 있다. quota는 **요청 좌석 수가 아니라 실제 변경된 행 수**만큼 줄여야 한다. 세 경로 모두 같은 원칙이 필요하다.

3. **만료 스위퍼의 quota 감소를 누가 수행하는가.** 스위퍼는 사용자 요청이 아니라 배치다. 여러 사용자의 좌석을 한 벌크 UPDATE로 회수하므로, **사용자별로 몇 석씩 줄일지 집계해야 한다.** 현재 회수 SQL은 `affected_rows`만 돌려주고 사용자별 내역을 알려주지 않는다.

4. **카운터 정합성이 깨졌을 때의 복구.** 어느 경로 하나가 감소를 빠뜨리면 사용자는 영구히 예매 불가 상태가 된다. 정합성 검사 쿼리와 보정 수단이 필요하다.

### 그 밖

| 항목 | 상태 |
|---|---|
| `@Scheduled` 스위퍼 배선 | 미구현. Task 2D의 스위퍼를 호출하는 주체가 여전히 없다 |
| 규칙 32 감사 로그 | 미구현. **해제도 `hold_id`·`held_by`·`held_at`을 지우므로 "누가 언제 놓았는지"가 사라진다** |
| 규칙 35 메트릭 | 미구현. 해제율은 좌석 회전율의 직접 지표다 |
