## 4. 실험 A — 후보와 반환 타입

### 문제

운영 `ExpiryCandidate` 는 `(seatId, holdId)` 뿐이다. quota 를 정산하려면 소유자와 회차가 필요하다.

### 비교한 네 대안

| 대안 | 판단 |
|---|---|
| 운영 `ExpiryCandidate` 에 `heldBy` 추가 | ❌ 좌석 만료 저장소가 quota 정책에 결합된다. 게다가 **후보 시점 소유자일 뿐** 실제 회수 성공을 말해주지 않는다 (2G-C §3) |
| quota 정산 전용 후보 타입을 따로 도입 | △ 타입이 하나 늘 뿐 조회는 여전히 필요하다 |
| **후보 조회 결과를 `(saleEventId, userId)` 그룹으로 반환** | ✅ **채택** |
| 기존 후보 유지 + 별도 조회로 사용자를 구함 | ❌ 후보 조회와 사용자 조회 사이가 또 벌어진다 |

### 채택 계약

- **운영 `ExpiryCandidate` 를 바꾸지 않는다.** 스위퍼(호출자)가 `held_by` 와 `sale_event_id` 를
  포함한 자기 조회를 하고 그룹으로 묶는다. 좌석 회수 자체는 운영 `expire(List<ExpiryCandidate>)`
  를 **그룹마다** 호출한다 — 그러면 각 호출의 `affected_rows` 가 곧 그 사용자의 실제 회수 수다.
- **후보 시점 소유자와 실제 회수를 혼동하지 않는다.** 감소량은 항상 `affected_rows` 다.
- **반환은 `int` 하나로 부족하다.** 최소 계약은 §11.

### 책임 경계

| 계층 | 책임 |
|---|---|
| `JdbcSeatExpiryRepository` (운영, 변경 없음) | 좌석 회수의 조건부 UPDATE 와 `affected_rows` |
| 스위퍼 (2G-G·2H) | 후보 그룹화, quota 잠금 순서, 트랜잭션 경계, 재시도 |
| quota 저장소 (2G-G) | 카운터 행의 조건부 UPDATE |

## 5. 실험 B — 배치 원자성과 사용자별 트랜잭션

### ★ 실패 재현 — 배치 전체 트랜잭션의 손해

사용자 A(3석)와 B(2석)의 좌석이 모두 만료됐고, **B 의 quota 행만 없다.**

| | 배치 전체 트랜잭션 | 사용자별 트랜잭션 |
|---|---|---|
| 회수 | **0석** | **3석** (A) |
| A 의 좌석 | `HELD` 로 남음 ★ | `AVAILABLE` |
| A 의 카운터 | 3 그대로 | 0 |
| B 의 좌석 | `HELD` | `HELD` |
| B 의 카운터 행 | 없음 (만들지 않음) | 없음 (만들지 않음) |

**A 는 잘못한 것이 없는데 좌석이 회수되지 않는다.** B 의 카운터가 없다는 사실과 A 의 좌석이
만료됐다는 사실은 아무 관계가 없다. 한 사용자의 drift 가 I-10 회수 전체를 멈춘다.

> 이 테스트가 통과한다는 것은 그 손해를 **관측했다**는 뜻이지 그 방식이 옳다는 뜻이 아니다
> (규칙 27).

### ✅ 채택 — 사용자별 트랜잭션

- `(saleEventId, userId)` 그룹마다 독립 트랜잭션
- **그룹 안에서는 좌석 회수와 quota 감소가 원자적**이다 — 좌석만 풀리고 카운터가 남는
  반쪽 상태가 없다 (테스트로 고정)
- 실패 그룹은 좌석도 카운터도 바뀌지 않는다
- 정상 그룹은 다른 사용자의 drift 때문에 롤백되지 않는다
- 처리 순서는 quota 키 오름차순 (2G-B)
- 성공·실패 그룹을 호출자가 구분할 수 있다

**근거는 I-10 의 회수 가용성이다.** 만료 회수는 좌석을 다시 팔 수 있게 만드는 경로이고,
그것이 한 사용자의 데이터 손상으로 멈추면 정합성을 지키려다 가용성을 잃는다.
사용자 단위 정합성은 그룹 트랜잭션이 이미 보장한다.

### 부수 효과 — 실패 그룹은 좌석 SQL 을 보내지 않는다

quota 잠금이 좌석보다 먼저이므로(quota → seat) 행이 없으면 **좌석을 건드리기 전에 멈춘다.**
롤백할 좌석 변경 자체가 생기지 않는다.

## 6. 실험 C — quota 행 부재

### 비교한 네 대안

| 대안 | 판단 |
|---|---|
| 전체 배치 중단 | ❌ §5 의 손해. 무관한 사용자의 회수가 멈춘다 |
| **해당 그룹만 실패하고 나머지 계속** | ✅ **채택** |
| quota 행을 자동 생성한 뒤 감소 | ❌ 아래 |
| 행 부재를 무시하고 좌석만 회수 | ❌ 아래 |

### 자동 생성과 무시를 기각한 이유

둘 다 **drift 를 숨긴다.**

- **자동 생성** — 행이 없다는 것은 그 사용자의 좌석이 카운터에 집계된 적이 없다는 뜻이다.
  0 으로 만들고 감소하면 음수가 되거나(CHECK 위반) 0 에 머문다. 어느 쪽이든 **원인은
  조사되지 않은 채 증상만 사라진다.**
- **무시하고 좌석만 회수** — 좌석은 풀리고 카운터는 그대로다. 그 사용자는 이후 실제보다
  적게 잡을 수 있고, 아무도 그 사실을 모른다.

### 채택 계약

| 항목 | 계약 |
|---|---|
| 해당 그룹의 좌석 | **변경하지 않는다** (잠금 단계에서 멈춘다) |
| 해당 그룹의 quota | **변경하지 않는다.** 행을 만들지 않는다 |
| 다른 사용자 그룹 | **계속 처리한다** |
| 결과에 담을 정보 | 그룹 키, 실패 종류(`QUOTA_ROW_MISSING`), 원인 메시지, 시도 횟수 |
| 알람·메트릭 | 실패 그룹 수, 종류별 분포, 연속 실패 회차 |
| 자동 복구 | **하지 않는다** |

**quota 감소 거부**(카운터가 실제보다 작아 음수가 될 요청)도 같은 계약이다 —
`QUOTA_DECREASE_REJECTED` 로 그 그룹만 롤백한다.

## 7. 실험 D — 다중 스위퍼

### 질문

운영 `JdbcSeatExpiryRepository` 는 "중복 실행은 정합성 문제가 아니라 효율 문제" 라고 적었다.
그것은 **좌석만** 볼 때의 이야기다. quota 감소가 붙으면 달라진다 —
**두 스위퍼가 같은 후보를 보고 각자 카운터를 줄이면 이중 감소가 되는가?**
2G-C 가 미검증으로 남긴 항목이다.

### 검증 방법 — 같은 후보를 봤다는 것을 보장한다

**출발선 래치만으로는 부족하다.** `sweep()` 호출 시각만 맞추면 첫 스위퍼가 정산까지 끝낸 뒤
나머지가 빈 후보를 조회할 수 있다. 그래도 최종 quota 와 좌석 상태는 정상이라
**테스트는 통과하지만 경합이 일어나지 않아 아무것도 검증하지 못한다.**

그래서 후보 조회 직후 훅에서 **두 단계 배리어**를 친다.

```
1. 후보 조회 완료를 알림 (allCandidatesSelected)
2. 모든 스위퍼가 조회를 끝낼 때까지 대기   ← 아무도 먼저 정산하지 못한다
3. 각 스위퍼의 시나리오 훅 실행 (확정 등)
4. 훅 완료를 알림 (allPostSelectHooksCompleted)
5. 모든 훅이 끝날 때까지 대기              ← 정산은 이 뒤에 시작된다
```

배리어 대기에는 timeout 이 있고, **시간 초과와 interrupt 를 조용히 넘기지 않는다** —
배리어가 깨진 채 통과하면 그것이야말로 검증되지 않은 통과다.

**배리어가 동작했다는 증거로 각 스위퍼의 `candidatesFound()` 가 모두 같은지 확인한다.**
최종 quota 와 좌석 상태만 보면 경합이 실제로 일어났는지 알 수 없다.

> **정직한 단서.** 배리어를 일시적으로 무력화하고 돌려도 이 환경에서는 통과했다.
> 즉 배리어는 "실패하던 것을 고친" 것이 아니라, **타이밍 운에 맡겨져 있던 순서를
> 결정적으로 고정한** 것이다. CI 부하나 머신이 달라지면 그 운은 달라질 수 있다.

`Thread.sleep` 은 쓰지 않는다 (규칙 25). 모든 `Future` 의 결과·예외를 회수하고
제한 시간 안의 종료를 단정한다. 근거는 반복 횟수가 아니라 **최종 DB 상태의 구조적 불변식**이다.

### 결과 (배리어 통과 후)

| 검증 | 결과 |
|---|---|
| **모든 스위퍼가 같은 후보 수를 읽음** | 배리어 통과 후 2·3·4·6대 전부 동일 (`candidatesFound`) |
| 같은 후보를 본 2대 — quota 이중 감소 | **없음.** 4석 → 카운터 4→0 |
| 좌석 `version` 증가 | **정확히 1** (각 좌석) |
| quota 감소 합계 = 실제 회수 행 수 | 일치 (2사용자 5석) |
| 최종 카운터 = 활성 좌석 수 | 일치 (A 4석 중 2석만 만료 → 카운터 2) |
| `SOLD` 좌석 | 유지됨 (I-11) |
| 스위퍼 6대 | 회수는 여전히 4석뿐 |
| 데드락 | **발생하지 않음** |
| 실패한 스위퍼 | **0건** |

**실측: 스위퍼 4대 중 회수한 것은 1대, 총 회수 4석, 실패 0건.**

### 왜 안전한가 — 구조적 논증

이중 감소가 없는 이유는 **감소량이 그 그룹의 `affected_rows` 이기 때문**이다.
같은 좌석을 두 스위퍼가 회수하려 하면 조건부 UPDATE 가 한쪽만 통과시키고,
진 쪽은 `affected_rows = 0` 이라 **감소 SQL 자체를 보내지 않는다.**
후보 수로 감소했다면 이중 감소가 났을 것이다 (2G-C 의 결정이 여기서 값을 한다).

### ✅ 채택 계약

확정과의 경쟁도 같은 배리어를 쓴다 — **모든 스위퍼가 확정 전 후보를 읽고**, 지정된 훅에서
확정이 일어나고, **확정이 끝난 뒤에 모두 정산한다.** 그 순서에서 확정된 좌석은 어느 스위퍼도
회수하지 않았다.

- **다중 스위퍼를 허용한다.** 잡 락을 정확성의 필수 조건으로 두지 않는다.
- ShedLock 등 단일 인스턴스 강제는 **효율 최적화 후보**다. 도입 여부는 실제 중복 실행 비율과
  DB 부하를 측정한 뒤 판단한다.
- 잡 락 자체가 "그것이 죽으면 스위퍼 전체가 멈춘다" 는 **새 가용성 위험**을 만든다.

> **중복 실행의 대가는 헛일과 잠금 경합이다.** 정합성 문제가 아니라는 것이 이 실험의 결과이지,
> 비용이 없다는 뜻은 아니다.

## 8. 실험 E — 데드락 재시도 정책

### ★ 실제 MySQL 데드락 재현

두 트랜잭션이 같은 두 quota 행을 **반대 순서**로 잠근다 — 2G-B 가 "quota 키 오름차순" 을
정한 이유를 뒤집어 본 것이다.

```
[Task 2G-F] 데드락 최상위 예외 = CannotAcquireLockException
            root = MySQLTransactionRollbackException   (vendor code 1213)
```

### 분류 기준 — cause 사슬 전체를 훑는다

**최상위 예외 타입만 보면 안 된다.** 2G-B 가 관측한 것 —
**NESTED savepoint 가 1213 을 1305 로 덮는다.** 최상위만 보고 분류하면
재시도해야 할 데드락을 영구 실패로 처리한다.

### ★ vendor code 를 예외 클래스보다 우선하는 이유

**vendor code 만이 원인을 특정한다.** 1213(데드락)과 1205(잠금 대기 초과)는 운영에서 서로 다른
신호다 — 전자는 잠금 순서가 어긋났다는 뜻이고 후자는 잠금이 오래 잡혀 있다는 뜻이라
**고쳐야 할 곳이 다르다.** 예외 클래스는 그 구분을 담지 못한다.

그래서 판정 순서를 **아는 것이 많은 쪽부터** 둔다. 아래로 갈수록 분류도 덜 단정적이 된다.

| 순위 | 판정 기준 | 분류 | 아는 것 |
|---|---|---|---|
| 1 | cause 사슬의 vendor code **1213** | `DEADLOCK` | 원인까지 |
| 1 | cause 사슬의 vendor code **1205** | `LOCK_WAIT_TIMEOUT` | 원인까지 |
| 2 | `SQLTransactionRollbackException` (vendor code 없음) | **`TRANSIENT_TRANSACTION_ROLLBACK`** | "일시적 롤백" 까지만 |
| 3 | `PessimisticLockingFailureException` (Spring generic) | `TRANSIENT_LOCK_FAILURE` | "잠금 실패" 까지만 |

**cause 사슬 전체를 훑는 이유는 따로 있다.** NESTED savepoint 가 1213 을 1305 로 덮기
때문에(2G-B) 최상위 예외만 보면 재시도해야 할 데드락을 영구 실패로 처리한다.

### vendor code 가 없으면 이름을 빌려 오지 않는다

두 예외 타입 모두 **원인을 특정해 주지 않는다.** 그런데 이름을 빌려 오면 지표가 거짓말을 한다.

| 예외 | 실제로 알려 주는 것 | 잘못 붙였을 때 |
|---|---|---|
| `SQLTransactionRollbackException` | "이 트랜잭션은 롤백됐다" — deadlock 외에 **직렬화 실패** 등도 포함 | `DEADLOCK` 으로 세면 **데드락 지표가 부풀려져** 잠금 순서를 의심하게 된다. quota → seat 순서는 2G-B 가 이미 정한 것이라 "데드락이 늘었다" 는 곧 "그 순서가 깨졌다" 로 읽힌다 |
| `PessimisticLockingFailureException` | "잠금을 얻지 못했다" — 1205 처럼 **보유 시간**이 길어서인지 1213 처럼 **순서**가 어긋나서인지 모름 | `LOCK_WAIT_TIMEOUT` 으로 세면 **timeout 지표가 부풀려져** 트랜잭션 길이나 `innodb_lock_wait_timeout` 설정을 의심하게 된다 — 원인이 거기에 없을 수도 있는데도 |

두 `TRANSIENT_*` 를 서로도 구분하는 이유는 **나오는 지점이 다르기 때문**이다.
전자는 드라이버가 롤백을 알린 경우이고 후자는 Spring 이 잠금 실패로 번역한 경우라,
조사할 방향이 다르다.

**같은 예외 타입이라도 vendor code 가 붙어 있으면 그것이 이긴다** (순위 1) —
generic 잠금 예외 안에 1213 이 있으면 `DEADLOCK`, 1205 가 있으면 `LOCK_WAIT_TIMEOUT` 이다.

### 재시도는 하되 지표는 분리하는 이유

| | 재시도 | 지표가 가리키는 것 |
|---|---|---|
| `DEADLOCK` | ✅ | **잠금 순서** 문제 (2G-B 의 quota → seat, 규칙 2) |
| `LOCK_WAIT_TIMEOUT` | ✅ | **잠금 보유 시간** 문제 (긴 트랜잭션, 규칙 9의 3초 설정) |
| `TRANSIENT_TRANSACTION_ROLLBACK` | ✅ | **원인 미상** — 드라이버가 롤백을 알린 쪽 |
| `TRANSIENT_LOCK_FAILURE` | ✅ | **원인 미상** — Spring 이 잠금 실패로 번역한 쪽 |

**재시도 여부와 원인 분류는 별개의 문제다.** 원인은 몰라도 *일시적이라는 것*은
드라이버나 Spring 이 말해 줬으니 재시도한다. 그러나 이름을 빌려 오면 관측값이 거짓말을 한다.
분류를 나눈 것은 재시도 정책 때문이 아니라 **알람과 지표가 원인을 구분할 수 있게** 하기 위해서다.

### 재시도하지 않는 것

| 분류 | 이유 |
|---|---|
| `QUOTA_ROW_MISSING` · `QUOTA_DECREASE_REJECTED` · `CORRUPT_CANDIDATE` | 업무 실패. 재시도해도 결과가 같고 배치만 느려진다 |
| `UNKNOWN` (문법 오류, 무결성 오류 등) | 모르는 실패를 반복하면 원인을 감춘 채 부하만 늘린다 |

### ✅ 채택 계약

| 항목 | 계약 |
|---|---|
| 재시도 단위 | **실패한 사용자 그룹**. 전체 배치가 아니다 |
| 대상 | 일시적 실패만 — `DEADLOCK`(1213) · `LOCK_WAIT_TIMEOUT`(1205) · `TRANSIENT_TRANSACTION_ROLLBACK`(code 없는 JDBC 롤백) · `TRANSIENT_LOCK_FAILURE`(code 없는 Spring 잠금 실패) |
| 분류 | **재시도 여부와 원인 분류는 별개다.** 넷 다 재시도하되 이름은 섞지 않는다 |
| 최대 시도 | **최초 시도 포함 3회** → backoff 는 최대 2회 |
| 백오프 | **상한이 있는 방식**. 무한 증가하지 않는다. **구체적 값은 Task 2H 범위** |
| 트랜잭션 | 재시도마다 **새 트랜잭션** |
| 이미 커밋된 그룹 | **다시 실행하지 않는다** (테스트로 고정) |
| 업무 실패 | 1회 시도로 끝. 백오프도 호출하지 않는다 |

### ★ 분류만이 아니라 실제 재시도 루프를 검증했다

**분류가 맞아도 루프가 틀릴 수 있다.** 재시도하지 않거나, 이미 커밋된 그룹을 다시 실행하거나,
같은 트랜잭션에서 재시도하면 계약은 깨진다. 상수 확인으로는 알 수 없다.

그래서 **정산 트랜잭션 안에서** 실패를 던지는 테스트 전용 seam 을 두고 루프를 실제로 돌렸다.
주입한 예외의 cause 사슬에는 진짜 MySQL vendor code(1213/1205)를 넣어 **분류 경로를
우회하지 않는다.** 기본 생성 경로에서는 no-op 이라 다른 테스트에 영향이 없다.

| 시나리오 | 주입 | 결과 |
|---|---|---|
| **A** 두 번째 시도 성공 | 1회차에 1213 | 시도 2회, backoff 1회, **실패 그룹 아님**, 좌석·quota 정상 정산 |
| **B** 세 번째까지 실패 | 1205 × 3 | 시도 3회, backoff **2회**, **4번째 시도 없음**, `attempts=3`, 좌석·quota 불변 |
| **C** 성공 그룹 재실행 안 함 | B 그룹 1회차만 실패 | 훅 호출이 `A#1, B#1, B#2` — **A 는 한 번뿐**. 좌석 UPDATE 2회, quota 감소 2회, 회수 5석 |
| **D** 재시도마다 새 트랜잭션 | 1회차에 1213 | `attempt#1 begin → ROLLED_BACK → backoff#1(active=false) → attempt#2 begin → COMMITTED`, TX 2개 |
| **E** transient rollback 도 재시도 | 1회차에 **vendor code 없는** `SQLTransactionRollbackException` | 시도 2회, backoff 1회, 정상 정산. **분류는 `TRANSIENT_TRANSACTION_ROLLBACK` 이고 `DEADLOCK` 이 아니다** |
| **F** generic 잠금 실패도 재시도 | 1회차에 **vendor code 없는** `PessimisticLockingFailureException` | 시도 2회, backoff 1회, 정상 정산. **분류는 `TRANSIENT_LOCK_FAILURE` 이고 `LOCK_WAIT_TIMEOUT`·`DEADLOCK` 이 아니다** |
| 네 일시적 원인이 결과에서 구분됨 | 1213 / 1205 / code 없는 JDBC rollback / code 없는 Spring generic lock 각각 3회 | **네 실패 결과의 `kind` 가 모두 다르고** 각각 `attempts=3`, backoff 2회 |
| 업무 실패는 루프 안 돎 | 감소 거부 | 훅 1회, backoff 0회, `attempts=1` |

D 는 `TransactionSynchronization.afterCompletion` 으로 각 시도의 트랜잭션 종료를 관찰하고,
**backoff 시점에 이전 트랜잭션이 활성이 아님**(`isActualTransactionActive() == false`)을 확인한다.

C 에서 관측된 부수 효과 — **실패한 시도는 좌석 UPDATE 를 아예 보내지 않는다.**
주입 훅이 좌석 갱신 앞에 있고, 실제 운영에서도 quota 잠금이 좌석보다 먼저이므로
롤백할 좌석 변경이 생기지 않는다.

> **최대 3회는 최초 시도를 포함한다.** 따라서 backoff 는 최대 2회다 (B 에서 실측).

### 테스트를 느리게 만들지 않는다

백오프는 주입 가능한 전략으로 두고 테스트는 **0 지연**을 쓴다. 실제 대기 시간에 의존하면
테스트가 느려지기만 하고 검증되는 것은 없다. **운영의 구체적 백오프 값은 문서로만 정한다** —
실측 없이 숫자를 확정하지 않는다.

## 9. 실험 F — `held_by NULL`

### 문제

`status IN ('HELD','PAYING')` 이고 `hold_id` 는 있는데 `held_by` 가 NULL 인 행.
소유자를 모르므로 **어느 카운터를 줄여야 할지 알 수 없다.**

운영 후보 조회는 `hold_id IS NOT NULL` 로 거르지만 `held_by` 는 보지 않는다.

### 비교

| 대안 | 판단 |
|---|---|
| 배치 전체 실패 (2G-C 의 coordinator 방식) | ❌ 손상 행 하나가 모든 사용자의 회수를 멈춘다 |
| **손상 후보만 격리해 보고** | ✅ **채택** |
| 조용히 후보에서 제외 | ❌ 그 좌석은 영원히 회수되지 않으면서 아무도 모른다 |
| 소유자를 추측해 정산 | ❌ 사용자 0 같은 존재하지 않는 그룹이 생긴다 |

### ✅ 채택 계약 (테스트로 고정)

- 조용히 제외하지 **않는다** — 결과의 `corrupt` 목록에 좌석 ID 와 원인이 남는다
- 사용자 그룹을 추측하지 **않는다** — `getLong` 이 NULL 을 0 으로 돌려주는 것을 막는다
- 해당 좌석을 quota 정산 없이 해제하지 **않는다**
- **정상 사용자 그룹의 만료를 막지 않는다** (배치 전체 실패를 기각한 이유)
- 자동 보정하지 **않는다** — 다음 배치에서도 다시 보고된다

`hold_id` 가 NULL 인 활성 좌석도 같은 방식으로 손상 후보로 분리한다.

### 남는 문제

**이 좌석들은 여전히 회수되지 않는다.** 격리는 안전한 처리이지 해결이 아니다.
발생 원인 조사와 DB CHECK 도입 여부는 **미결정**이다 (§13).

## 10. 실험 G — drift 탐지와 보정

### 탐지 쿼리

`user_hold_quota.held_seats` 와 같은 `(sale_event_id, user_id)` 의 활성 좌석 수를 대조한다.
경로는 `seat_inventory → train_schedule` (2G-E-B2 의 정규화 조인, `STRAIGHT_JOIN` 고정).
활성은 `HELD`·`PAYING` 뿐이다.

**MySQL 에 `FULL OUTER JOIN` 이 없어 두 방향을 각각 본다.** 한쪽만 보면
"카운터 없이 좌석만 있는" 경우를 놓친다 — 상한 검사를 완전히 무력화하는 가장 위험한 방향이다.

### 탐지하는 여섯 가지

| 종류 | 의미 | 결과 |
|---|---|---|
| `QUOTA_WITHOUT_SEATS` | 카운터는 있는데 활성 좌석이 없다 | 탐지됨 |
| `SEATS_WITHOUT_QUOTA` | 활성 좌석은 있는데 카운터 행이 없다 ★ | 탐지됨 |
| `QUOTA_GREATER` | 카운터가 실제보다 크다 | 탐지됨 |
| `QUOTA_LESS` | 카운터가 실제보다 작다 | 탐지됨 |
| `held_by NULL` 활성 좌석 | 어느 카운터에도 집계되지 않는다 | **별도 쿼리** |
| 음수·상한 초과 | — | **DB CHECK 가 애초에 막는다** |

**`held_by NULL` 은 대조 쿼리로 보이지 않는다.** 그 좌석이 집계에서 빠지므로
카운터와 집계가 "맞아 보인다". 테스트가 이 사각지대를 명시적으로 재현한다.

### 보정 정책

| 대안 | 판단 |
|---|---|
| DB 값을 자동으로 좌석 집계에 맞춤 | ❌ 아래 |
| **자동 보정하지 않고 알람 + 수동 절차** | ✅ **채택** |
| 특정 방향의 drift 만 자동 보정 | ❌ 아래 |

**좌석과 quota 중 무엇이 진실의 원천인지 근거 없이 정하지 않는다.**
어느 쪽이 틀렸는지는 drift 의 원인에 따라 다르다.

- 감소 누락이면 좌석이 옳다
- 확정 경로의 quota 감소 부재(2G-C 의 미해결 항목)라면 **카운터가 "옳게" 크다** —
  그것을 좌석에 맞추면 진짜 문제를 지운다
- 카운터 없이 좌석만 있는 경우는 아예 다른 사고다

**방향별 자동 보정도 기각한다.** 방향은 증상이지 원인이 아니다.

### ✅ 채택 계약

- 탐지는 **읽기 전용**이다. 이번 Task 에서 보정 SQL 을 실행하지 않는다 (테스트로 고정)
- 반복 실행해도 결과가 같다 (멱등)
- 정합한 상태에서는 아무것도 탐지되지 않는다 — 그래야 탐지가 신호가 된다
- 보정은 **원인 조사 후 수동 절차**로 한다

## 11. 운영 결과 타입 — 최소 계약

`int` 하나로는 다음을 구분할 수 없다. **셋 다 0 이다.**

- 만료 후보가 없었다
- 후보가 전부 stale 했다
- 모든 그룹이 drift 로 실패했다

### 최소 계약 (이름은 Task 2H 가 정한다)

| 정보 | 왜 필요한가 |
|---|---|
| 조회한 후보 수 | stale 비율 계산의 분모 |
| 실제 회수 수 | I-10 진척 |
| **성공한 사용자 그룹과 회수 수** | quota 감소의 근거 |
| **실패한 그룹과 실패 종류·원인** | 알람이 가리킬 대상 |
| stale 후보 수 | 경합 정도. 배치 크기 조정의 근거 |
| **손상 후보 목록** | 영원히 회수되지 않는 좌석의 존재 |
| 재시도 횟수 | 경합 추세 |
| 배치 시작·종료 시각 | 배치 주기 조정 |

실험에서는 `Task2gfSweepOutcome` 으로 검증했다. **운영 타입 이름과 패키지는 확정하지 않는다** —
애플리케이션 서비스가 실제로 무엇을 쓰는지 보고 2H 에서 정한다.

| 사용자 50명 · 2석 | 배치 전체 | 1 | 50 | 50 | 50 | **151** | 1 | 51ms |
| | 사용자별 | 1 | 50 | 50 | 50 | **151** | **50** | 121ms |

### ★ SQL 호출 수는 두 대안이 같다

늘어나는 것은 **트랜잭션 수뿐**이다. "사용자별 트랜잭션은 SQL 이 많아진다" 는 직관이 틀렸다.
quota 잠금·좌석 UPDATE·quota 감소는 어느 쪽이든 **그룹당 한 번**이기 때문이다.

### ★ 실패 그룹이 있을 때의 처리량

사용자 10명·후보 40개 중 **한 명의 카운터 행만 없을 때:**

| 대안 | 회수 | 성공 그룹 |
|---|---|---|
| 배치 전체 | **0석** | 0 |
| 사용자별 | **36석** | 9 |

**이것이 결정의 실질적 근거다.** SQL 수가 같은데 실패 시 결과가 이만큼 다르다.

### ★ 후보 조회의 실행 계획

2G-F 의 후보 조회는 운영 `JdbcSeatExpiryRepository` 와 달리 **`train_schedule` 조인이 붙는다.**
옵티마이저의 선택지가 늘었으므로 운영과 같은 `FORCE INDEX (idx_seat_inventory_expiry_candidate)`
를 걸고 EXPLAIN 으로 강제한다. **테스트가 스위퍼의 SQL 상수를 그대로 EXPLAIN 한다** —
복사본을 두면 실제 SQL 이 바뀌어도 검증이 눈치채지 못한다
(`SeatExpiryCandidateFairnessTest` 와 같은 방식).

| 검증 | 결과 |
|---|---|
| 구동 테이블 | `seat_inventory` |
| 사용 인덱스 | `idx_seat_inventory_expiry_candidate` (V2) |
| `train_schedule` 조인 | `eq_ref` / `PRIMARY` |
| 풀 스캔 | 없음 |
| filesort | **없음** — `ORDER BY expires_at, id` 가 인덱스로 해결된다 |

**backlog 를 늘려도 읽는 행 수가 늘지 않는다 (실측).**

| 전체 좌석 | 배치 크기 | 읽은 행 수 |
|---|---|---|
| 40행 | 20 | **21** |
| 200행 (5배) | 20 | **21** |

filesort 가 생기면 `LIMIT` 이 조기 종료하지 못해 만료 후보 **전부**를 읽어 정렬한 뒤 잘라낸다.
그러면 배치 비용이 배치 크기가 아니라 **backlog 크기**에 비례한다 (V2 마이그레이션 주석).
위 수치가 그 조기 종료가 실제로 일어난다는 증거다.

`held_by IS NOT NULL` 을 붙이지 않는 계약은 그대로다 — 손상 후보를 조용히 빼지 않기 위해서다.

### 배치 크기와 그룹 수의 관계

P-2 상한(4석) 때문에 **사용자당 후보는 4를 넘을 수 없다.**
따라서 후보 `N` 개인 배치의 그룹 수는 최소 `ceil(N/4)` 이고,
**트랜잭션 수의 하한이 배치 크기로 정해진다.**

> **실행 시간은 환경 의존 관측값으로만 기록한다** (규칙 30·31).
> 트랜잭션 수가 늘면 커밋 왕복이 늘어난다는 방향은 실측과 일치하지만,
> 절대 시간을 성능 보장으로 읽지 않는다. 깨지기 쉬운 시간 assertion 도 만들지 않았다.

## 13. 검증 결과

`./gradlew :modules:reservation-infra:test --rerun-tasks` — 실제 MySQL 8.4 Testcontainers,
H2 없음 (규칙 26).

| 테스트 | 다루는 실험 |
|---|---|
| `ExpiryBatchIsolationExperimentTest` | B(배치 원자성) · C(quota 행 부재) · F(손상 후보) · stale |
| `MultiSweeperQuotaSettlementTest` | D(다중 스위퍼) |
| `ExpirySweeperRetryContractTest` | E(데드락 분류·재시도) |
| `ExpiryQuotaDriftDetectionTest` | G(drift 탐지) |
| `ExpirySweeperCostMeasurementTest` | §12 비용 |

### 검증한 것

- 실패가 없으면 두 트랜잭션 대안의 결과가 같다
- **quota 행 부재 시 배치 전체는 정상 사용자의 회수까지 되돌린다** (실패 재현)
- 사용자별 트랜잭션은 정상 그룹만 커밋한다
- 실패 그룹에 좌석만 풀리거나 quota 만 줄어드는 반쪽 상태가 없다
- 처리 순서가 quota 키 오름차순이다
- quota 감소 거부도 그 그룹만 롤백한다
- 손상 후보를 보고하고, 회수·추측·보정하지 않으며, 정상 그룹을 막지 않는다
- 후보 조회 뒤 확정된 좌석은 stale 로 집계되고 **후보 수가 아니라 회수 수만큼 감소**한다
- **다중 스위퍼가 두 단계 배리어를 통과해 같은 후보를 봤다** — 각 스위퍼의
  `candidatesFound` 가 모두 같음을 결과로 확인
- **다중 스위퍼에서 quota 이중 감소가 없다.** 좌석 `version` 은 정확히 1 증가
- 최종 카운터와 활성 좌석 수가 일치한다
- 확정과의 3자 경쟁에서 `SOLD` 가 유지된다 (I-11)
- **실제 MySQL 1213 을 재현하고 cause 사슬로 분류한다**
- savepoint 가 덮은 1305 아래의 1213 도 찾아낸다
- generic 잠금 예외만으로 데드락이라고 단정하지 않는다
- **vendor code 없는 `SQLTransactionRollbackException` 을 데드락으로 세지 않는다**
- **vendor code 없는 `PessimisticLockingFailureException` 을 timeout 으로 세지 않는다**
- 같은 예외 타입이라도 vendor code(1213·1205)가 붙어 있으면 그것이 이긴다
- **네 일시적 원인이 실패 결과에서 서로 구분된다** (`doesNotHaveDuplicates`)
- 업무 실패를 잠금 실패로 오분류하지 않는다
- **실제 재시도 루프를 실패 주입으로 검증한다** — 2회차 성공, 3회로 중단(4번째 없음),
  성공 그룹 재실행 없음, 재시도마다 새 트랜잭션,
  **vendor code 없는 롤백·generic 잠금 실패도 재시도**
- **backoff 는 최대 2회** (최초 시도 포함 3회이므로)
- 후보 조회가 **운영과 같은 인덱스를 강제하고 filesort 가 없다**
- **backlog 가 5배가 돼도 읽는 행 수가 같다** (21행 → 21행)
- drift 여섯 방향을 각각 탐지하고, `held_by NULL` 사각지대를 별도로 잡는다
- 탐지가 아무것도 고치지 않는다 (멱등)
- **SQL 호출 수는 두 대안이 같고 트랜잭션 수만 다르다**

### 검증하지 않은 것

- **운영 구현 전체** — 마이그레이션·저장소·스케줄러·재시도 컴포넌트를 만들지 않았다
- **실제 백오프 값** — 0 지연으로만 검증했다. **구체적인 대기 시간과 증가 방식은
  Task 2H 의 범위**이며 이 문서는 "상한이 있어야 한다" 는 형태만 정한다.
  실측 없이 숫자를 확정하지 않는다
- **`TRANSIENT_*` 두 분류의 실제 발생 빈도** — 운영에서 얼마나 나오는지 모른다.
  주입으로 동작만 확인했다. 이 둘이 대부분을 차지하면 vendor code 가 cause 사슬에
  실리지 않는 경로가 있다는 뜻이지만, 그 조사는 하지 않았다
- **배리어 없이도 실패하는 조건** — 배리어를 빼도 이 환경에서는 통과했다.
  배리어는 순서를 **보장**할 뿐 "고장을 고친" 것이 아니다
- **주입한 데드락은 실제 잠금 경합이 아니다** — 루프 동작을 결정적으로 보려고
  같은 cause 사슬을 가진 예외를 던졌다. 실제 1213 재현은 §8 §1 이 따로 한다
- **확정·해제 경로의 quota 감소** — 2G-C 가 남긴 미해결 항목 그대로다
- **`held_by NULL` 의 발생 원인** — 여전히 미상이다
- **대규모 배치의 잠금 경합** — 사용자 50명이 상한이었다
- **다중 스위퍼의 실제 중복 비율과 DB 부하** — ShedLock 판단에 필요한 측정이다
- **전체 시스템의 deadlock-free** — 만료 경로 안에서만 봤다
