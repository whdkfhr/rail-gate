# 실험 — 좌석 선점 경쟁 조건 재현과 조건부 UPDATE의 효과

> TASK-002A · 2026-08-02
> 관련: [INVARIANTS.md](../INVARIANTS.md) I-8, [CLAUDE.md](../../CLAUDE.md) 규칙 1·27

## 목적

**"한 번도 실패한 적 없는 동시성 테스트는 테스트가 아니다"** (CLAUDE.md 규칙 27).

조건부 UPDATE가 실제로 무언가를 막고 있음을 보이려면, 그것이 없을 때 **같은 조건에서 실제로 깨지는 것**을 보여야 한다. 이 문서는 그 재현 절차와 결과를 기록한다.

INVARIANTS.md의 3층 주장 구조에서 이 실험은 **결정적 검증** 층에 해당한다. 구조적 논증은 아래 §4에 따로 둔다.

---

## 1. 환경

| 항목 | 값 |
|---|---|
| DB | MySQL 8.4 (Testcontainers) |
| 격리 수준 | REPEATABLE READ (InnoDB 기본) |
| 커넥션 풀 | HikariCP, max 64 |
| 세션 설정 | `innodb_lock_wait_timeout = 3` |
| 워커 | Java 21 가상 스레드 |
| 대상 | `seat_inventory` 행 1개 (`UNIQUE (schedule_id, seat_no)`) |

임베디드 DB를 쓰지 않았다. H2 등은 행 잠금 동작이 InnoDB와 달라, 검증하려는 성질 자체가 재현되지 않는다 (CLAUDE.md 규칙 26).

---

## 2. 재현 방법 — `Thread.sleep` 없이 결정적으로

`Thread.sleep`으로 레이스 창을 벌리면 머신 부하에 따라 재현되기도 안 되기도 한다. 그런 테스트는 아무것도 보장하지 못한다 (CLAUDE.md 규칙 25).

대신 **`CyclicBarrier`로 제어 흐름을 고정**했다. 전원이 상태를 읽은 뒤에야 UPDATE를 시작하게 만들면, 창의 크기가 타이밍이 아니라 프로그램 구조로 결정된다.

```
순진한 구현 (테스트 전용)                    조건부 UPDATE (운영 코드)
────────────────────────────────────      ──────────────────────────────────
SELECT status WHERE id=?                   (읽기 없음)
  → 전원이 AVAILABLE 관측
        │                                          │
   ◀━ barrier ━▶  전원 대기                   ◀━ barrier ━▶  전원 대기
        │                                          │
UPDATE ... WHERE id=?                      UPDATE ... WHERE id=?
  (상태 조건 없음)                              AND status='AVAILABLE'
  → 전원 성공                                  → affected_rows 로 1명만 성공
```

**핵심: 조건부 UPDATE에는 벌릴 창이 없다.** 검사와 갱신이 한 문장이므로 그 사이에 배리어를 넣을 지점 자체가 존재하지 않는다. 이것이 두 구현의 유일한 차이다.

순진한 구현은 `src/test/java`에만 존재한다 (`NaiveSeatHoldRepository`). 운영 코드에는 남기지 않는다.

## 3. 결과

### A. 순진한 구현 — 초과 선점 발생

8명 동시 요청 (배리어로 전원이 SELECT 완료 후 UPDATE):

| 지표 | 값 |
|---|---|
| 성공 응답 | **8건** |
| 경합 실패 응답 | 0건 |
| 시스템 오류 | 0건 |
| **DB에 기록된 `hold_id`** | **1개** |

**7명이 "선점 성공"을 응답받고도 좌석을 갖지 못했다.** 좌석 행은 하나이고 `hold_id`는 마지막 UPDATE를 실행한 세션의 것이다.

실제 서비스라면 7명이 결제 화면으로 진입하고, 결제까지 마친 뒤에야 좌석이 없다는 것을 알게 된다. 오류 로그는 한 줄도 남지 않는다 — 모든 UPDATE가 정상 성공했기 때문이다.

### B. 조건부 UPDATE — 같은 조건에서 1명만 성공

동일한 배리어, 동일한 8명:

| 지표 | 값 |
|---|---|
| 성공 응답 | **1건** |
| 경합 실패 응답 | 7건 |
| 시스템 오류 | 0건 |
| DB에 기록된 `hold_id` | 1개 |

### C. 두 구현의 결정적 차이

**성공 응답 수와 실제 보유자 수가 일치하는가.**

| | 성공 응답 | 실제 보유자 | 일치 |
|---|---|---|---|
| 순진한 구현 | 8 | 1 | ❌ |
| 조건부 UPDATE | 1 | 1 | ✅ |

### D. 1,000명 규모

| 지표 | 값 |
|---|---|
| 동시 요청 | 1,000 (`CountDownLatch`로 동시 출발) |
| 성공 | **1건** |
| 경합 실패 | **999건** |
| 시스템 오류 | **0건** |
| 소요 시간 | **0.14초** |
| 최종 DB 상태 | 성공 응답을 받은 사용자와 `hold_id`·`held_by` 일치 |

경합 실패 999건은 **오류가 아니다.** 앱 계층에서 409로 매핑하며 오류율에 포함하지 않는다 (CLAUDE.md 규칙 21).

## 4. 왜 조건부 UPDATE가 좌석 선점 경쟁을 막는가 — 구조적 논증

> **범위 주의.** 이 절이 논증하는 것은 `AVAILABLE → HELD` 경쟁에서 정확히 하나만 통과한다는 것이다.
> I-8의 문장은 "하나의 좌석은 **최종적으로 한 예약에만 확정된다**"이고, 확정 단계
> (`PAYING → SOLD ... WHERE hold_id=?`)는 아직 구현되지 않았다. **I-8은 여기서 완결되지 않는다.**

부하 테스트나 동시성 테스트는 "위반이 관측되지 않았다"를 보일 뿐이다. **"위반이 불가능하다"는 아래 논증이 담당한다.**

세 가지가 겹쳐서 성립한다.

### (1) 좌석당 행이 물리적으로 하나뿐이다

```sql
UNIQUE KEY uk_seat_inventory_seat (schedule_id, seat_no)
```

이 제약 때문에 **"같은 좌석을 두 명이 선점"은 "같은 행을 `AVAILABLE`에서 두 번 전이"와 같은 말**이 된다. 문제가 행 하나의 문제로 환원된다.

> 좌석 재고를 카운터(남은 좌석 수)로 관리하면 이 성질이 사라진다. 여러 트랜잭션이 같은 값을 읽고 각자 감소시킬 수 있기 때문이다.

### (2) InnoDB가 같은 행의 갱신을 직렬화한다

두 세션이 같은 행을 UPDATE하면 한쪽이 배타적 행 잠금을 얻고 다른 쪽은 대기한다. **동시에 통과할 수 없다.**

### (3) 대기하던 쪽은 갱신된 값을 다시 평가한다

이 단계가 핵심이며 가장 오해받는 부분이다.

REPEATABLE READ에서 일반 `SELECT`는 트랜잭션 시작 시점의 스냅샷을 본다. 그래서 SELECT로 상태를 확인하면 다른 트랜잭션의 커밋이 보이지 않는다.

그러나 **UPDATE의 `WHERE` 절은 스냅샷이 아니라 현재 커밋된 값을 읽는다**(current read). 잠금이 풀린 뒤 조건을 재평가하므로, 앞선 세션이 `HELD`로 바꿨다면 `status='AVAILABLE'`이 불일치해 `affected_rows`가 0이 된다.

**결론:** (1)로 문제가 행 하나로 환원되고, (2)로 동시 통과가 불가능해지며, (3)으로 뒤늦게 도착한 요청이 반드시 실패한다. 세 단계 어디에도 애플리케이션 코드의 판단이 개입하지 않는다.

**단, 이 결론의 범위는 선점 단계다.** 한 좌석에 활성 홀드가 둘 이상 생기지 않는다는 것까지이며, "최종적으로 한 예약에만 확정"은 아래가 추가로 필요하다.

```sql
UPDATE seat_inventory
   SET status='SOLD', reservation_id=?, hold_id=NULL, held_by=NULL, expires_at=NULL
 WHERE id=? AND hold_id=? AND status='PAYING';
```

`hold_id` 조건이 없으면 남의 홀드를 확정하거나 만료 처리가 확정된 좌석을 해제한다 (I-11).

### 왜 성공 판정에 재조회를 쓰지 않는가

```java
int affectedRows = jdbc.update(HOLD_SQL, ...);
return affectedRows == 1 ? HELD : ALREADY_HELD;   // 재조회 없음
```

UPDATE 직후 `SELECT`로 확인하면 **또 하나의 창이 생긴다.** 그 사이 좌석이 만료되어 남에게 넘어가도 알 수 없고, 오히려 "성공했는데 남의 홀드를 확인"하는 결과가 나온다.

갱신을 수행한 그 문장이 몇 행을 바꿨는지가 **그 시점의 유일하게 신뢰할 수 있는 사실**이다.

## 5. 이 실험이 증명하지 못하는 것

- **테스트 통과는 증명이 아니다.** 이 실행에서 위반이 관측되지 않았다는 뜻이다. 동시성 버그는 특정 인터리빙에서만 나타나며, 무작위 부하가 그 인터리빙에 도달한다는 보장이 없다. §4의 구조적 논증이 함께 있어야 주장이 성립한다.
- **순진한 구현의 실패는 조건을 명시해야 한다.** 배리어로 창을 인위적으로 벌렸다. 다만 이 조건은 실제로 발생 가능하다 — GC pause, 네트워크 지연, 스케줄러 선점이 같은 효과를 낸다. 창을 벌린 것이 아니라 **창이 존재한다는 사실**을 드러낸 것이다.
- **절대 성능 수치가 아니다.** 0.14초는 로컬 Docker 환경의 값이며 프로덕션 처리량 근거로 쓸 수 없다.
- **I-8을 완결하지 못했다.** 확정 단계(`PAYING → SOLD ... WHERE hold_id=?`)가 없으므로 "최종적으로 한 예약에만 확정"은 아직 검증 대상이 아니다. 이 실험의 범위는 선점 경쟁까지다.
- **다좌석·1인당 상한은 다루지 않았다.** I-9는 단일 벌크 UPDATE의 `affected_rows` 검증이, I-12는 `user_hold_quota` 카운터 행이 담당하며 후속 Task다.
