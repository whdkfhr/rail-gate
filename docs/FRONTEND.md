# RailGate - 사용자 웹 클라이언트

> 상태: 목표 설계 v0.1 (2026-08-31)
> 현재 `apps/web-client`는 아직 없으며, 이 문서는 구현 범위와 계약을 먼저 고정한다.
> 관련 문서: [REQUIREMENTS.md](REQUIREMENTS.md), [ARCHITECTURE.md](ARCHITECTURE.md),
> [INVARIANTS.md](INVARIANTS.md)

---

## 1. 목적

RailGate의 사용자 웹은 장식용 포트폴리오 화면이 아니라, 백엔드가 보장하는 예매 상태를
사용자가 직접 확인하고 조작하는 실제 클라이언트다. 다음 흐름을 끊김 없이 제공한다.

```text
열차 검색 -> 대기열 -> 운행편 선택 -> 좌석 선택 -> 선점 -> 결제 -> 결과/예매 내역
```

화면은 대기, 경합, 만료, 결제 결과 미확정처럼 정상 성공보다 어려운 상태를 숨기지 않는다.
프론트엔드는 좌석 정합성의 최종 방어선이 아니며, 서버 응답을 임의로 성공으로 해석하지 않는다.

## 2. 기술 스택

| 영역 | 선택 | 선택 이유 |
|---|---|---|
| 언어·UI | TypeScript + React | API 응답과 예매 상태를 타입으로 제한하고 화면을 상태 단위 컴포넌트로 분리한다 |
| 빌드 | Vite | 별도 Spring API를 사용하는 SPA에 필요한 개발 서버와 번들링만 둔다 |
| 라우팅 | React Router Data Mode | 단계별 URL, 로딩, 오류 경계와 재진입 동작을 명시한다 |
| 서버 상태 | TanStack Query | 좌석·홀드·결제 조회, mutation, 재검증과 polling을 한곳에서 관리한다 |
| 폼 | React Hook Form + Zod | 검색·승객·결제 입력을 선언적으로 검증한다 |
| UI | Tailwind CSS + shadcn/ui + Lucide | 접근 가능한 기본 동작을 활용하되 RailGate 화면에 맞게 소스를 직접 조정한다 |
| API 모킹 | MSW | 백엔드 완성 전에도 성공·경합·만료·타임아웃 시나리오를 같은 HTTP 계약으로 개발한다 |
| 단위·통합 테스트 | Vitest + React Testing Library | 사용자 관점의 렌더링과 상태 전환을 검증한다 |
| E2E | Playwright | 데스크톱·모바일의 전체 예매 흐름과 포트폴리오 스크린샷을 검증한다 |

라이브러리 버전은 `apps/web-client`를 만드는 시점의 안정 버전으로 잠그고 lockfile을 커밋한다.
Spring API의 OpenAPI 문서에서 TypeScript 타입을 생성해 백엔드와 DTO를 이중 정의하지 않는다.

### 의도적으로 선택하지 않은 것

- **Next.js/SSR**: 검색 노출보다 로그인 이후의 운영형 예매 흐름이 중심이며 별도 Node 서버가
  주는 이점이 작다. 초기 구현은 Vite SPA로 충분하다.
- **Redux 기본 도입**: 서버 상태는 TanStack Query가 소유한다. 선택 좌석처럼 작은 UI 상태는
  컴포넌트 상태나 `useReducer`로 시작하고, 실제로 화면 간 공유가 커질 때만 별도 store를 둔다.
- **전 좌석 WebSocket 방송**: 좌석 전체를 실시간 동기화하지 않는다. 조회 재검증과 경합 응답을
  기본으로 하고, 대기 순번처럼 서버 push가 필요한 경로만 SSE를 사용한다.

## 3. 화면과 라우트

| 라우트 | 화면 | 핵심 상태 |
|---|---|---|
| `/search` | 열차 검색 | 출발역, 도착역, 날짜, 인원, 판매 회차 |
| `/queue/:eventId` | 대기열 | 대기 순번, 예상 시간, 정확도, SSE 연결·재연결·만료 |
| `/schedules` | 운행편 목록 | 시간, 소요 시간, 운임, 잔여 좌석, 매진·판매 마감 |
| `/schedules/:scheduleId/seats` | 좌석 선택 | 호차, 좌석 상태, 선택 목록, 1~4석 상한, 경합 |
| `/holds/:holdId/checkout` | 선점·결제 | 서버 만료 시각, 남은 시간, 금액, 결제 재시도 |
| `/payments/:paymentId/result` | 결제 결과 | 성공, 실패, `UNKNOWN`, 수동 확인 필요 |
| `/reservations` | 예매 내역 | 확정 좌석과 결제 상태 |

첫 화면은 소개용 랜딩 페이지가 아니라 `/search`의 실제 검색 도구다. 프로젝트 설명과 기술
근거는 README가 담당하고, 제품 화면 안에 포트폴리오 설명 문구를 넣지 않는다.

## 4. 서버 상태 표현 계약

### 대기열

- SSE 수신 중에는 순번과 예상 시간을 갱신한다.
- 연결이 끊기면 즉시 실패로 처리하지 않고 재연결 중임을 표시한 뒤 polling으로 폴백한다.
- `ACTIVE`가 되면 입장 토큰을 받은 뒤에만 좌석 화면으로 이동한다.
- 만료·취소 상태를 이전 순번으로 복원하지 않는다. 재등록은 새 순번을 받는 정책을 따른다.

### 좌석과 홀드

- 좌석은 최소한 `AVAILABLE`, 내가 선택, 다른 사용자 선점, 판매 완료를 구분한다.
- 색상만으로 상태를 구분하지 않고 텍스트·아이콘·비활성 상태를 함께 사용한다.
- `409`는 시스템 오류가 아니라 정상적인 경합 결과다. 실패 좌석을 표시하고 목록을 재조회한다.
- 카운트다운은 서버의 `expiresAt`을 기준으로 표시한다. 브라우저 타이머가 0이 되어도 로컬에서
  좌석을 해제했다고 단정하지 않고 서버를 재조회한다.
- 새로고침 후에도 URL의 `holdId`로 서버 상태를 복원하며 메모리 상태를 진실의 원천으로 삼지 않는다.

### 결제

- `202` 또는 `UNKNOWN`을 실패나 성공으로 바꾸지 않는다. 진행 중 화면에서 서버 상태를 polling한다.
- 재시도 버튼은 서버가 재시도를 허용한 경우에만 노출하고 동일 멱등키 정책을 따른다.
- `NEEDS_MANUAL_REVIEW`는 자동 재시도를 멈추고 확인 중 상태를 명확히 표시한다.

### 공통 HTTP 처리

| 응답 | 사용자 경험 |
|---|---|
| `202` | 처리 결과 확인 중, 상태 polling |
| `401` / `403` | 인증 또는 입장 토큰 재확인 |
| `409` | 좌석 경합·상태 변경 안내 후 최신 상태 재조회 |
| `429` | 입장 제한 또는 요청 상한 안내, 서버의 재시도 정책 준수 |
| `5xx` / 네트워크 오류 | 현재 선택을 성공으로 간주하지 않고 재조회·재시도 선택 제공 |

## 5. 상태 소유권

| 상태 | 소유자 | 예시 |
|---|---|---|
| 서버 상태 | TanStack Query 캐시 | 대기 순번, 좌석 상태, 홀드, 결제, 예매 내역 |
| URL 상태 | React Router | 판매 회차, 운행편, `holdId`, 검색 조건 |
| 폼 상태 | React Hook Form | 검색·승객·결제 입력 |
| 짧은 UI 상태 | 컴포넌트/`useReducer` | 열린 호차, 선택 좌석, 확인 대화상자 |

서버 데이터를 전역 store에 복제하지 않는다. 서로 다른 저장소에 같은 좌석 상태를 두면
무효화 순서에 따라 화면이 과거 상태를 표시할 수 있다.

## 6. 컴포넌트와 접근성 원칙

- 예매 도구답게 정보 밀도와 스캔 가능성을 우선하고 마케팅형 hero나 장식 카드를 만들지 않는다.
- 좌석 그리드는 행·열 크기를 고정해 선택, 로딩, 아이콘 변화가 레이아웃을 밀지 않게 한다.
- 모든 좌석은 키보드로 이동·선택할 수 있고 명확한 accessible name을 가진다.
- 포커스, 오류, 남은 시간 경고는 색상 하나에만 의존하지 않는다.
- 모바일에서도 검색, 좌석 선택, 결제의 주요 명령이 화면 밖으로 겹치거나 잘리지 않아야 한다.
- 서버 오류 원문, stack trace, 내부 식별자를 사용자에게 그대로 노출하지 않는다.

## 7. API 개발 방식

1. Task 2H에서 REST API와 OpenAPI 계약을 먼저 확정한다.
2. 프론트엔드는 생성된 타입과 얇은 HTTP adapter만 사용한다.
3. MSW handler는 정상 응답뿐 아니라 `409`, 만료, `202 UNKNOWN`, SSE 단절을 제공한다.
4. 실제 API가 준비되면 query/mutation 호출부는 유지하고 MSW만 비활성화한다.
5. 브라우저는 서비스 포트를 직접 알지 않는다. 개발 환경은 Vite proxy, 배포 환경은 Nginx의
   동일 origin `/api/queue`, `/api/reservations` 경로를 사용한다.

## 8. 테스트 완료 조건

### 컴포넌트·통합

- 4석 초과 선택을 요청 전에 차단하고 이유를 표시한다.
- `409` 응답 뒤 실패 좌석을 해제하고 최신 좌석을 다시 그린다.
- `expiresAt` 경계 전후의 카운트다운을 fake timer로 결정적으로 검증한다.
- `UNKNOWN` 결제는 성공 화면을 렌더링하지 않고 polling을 지속한다.
- SSE 단절 후 재연결 또는 polling 폴백으로 전환한다.

### Playwright E2E

- 대기열 등록부터 예약 확정까지 한 흐름이 완료된다.
- 두 브라우저가 같은 좌석을 선택하면 한쪽만 선점에 성공한다.
- 다좌석 중 하나가 stale이면 부분 선점이 화면과 DB 어디에도 남지 않는다.
- 홀드 만료 후 결제 진입이 거부되고 최신 좌석 상태가 보인다.
- 결제 `UNKNOWN`이 최종 성공·실패로 수렴한다.
- 데스크톱과 모바일 viewport에서 겹침·잘림이 없고 주요 흐름을 키보드로 완료할 수 있다.

E2E의 DB 사후 검증은 기존 `INVARIANTS.md`의 V-1~V-6 쿼리를 재사용한다. 화면 성공만으로
정합성을 증명했다고 간주하지 않는다.

## 9. 구현 순서

| Task | 범위 | 완료 조건 |
|---|---|---|
| FE-0 | `apps/web-client` 골격, 라우팅, 디자인 토큰, CI | build·lint·unit test가 Gradle check와 별도 CI에서 통과 |
| FE-1 | MSW 기반 검색·운행편·좌석 화면 | 정상·매진·경합 fixture와 반응형 좌석 화면 |
| FE-2 | 홀드·결제·예매 내역 | 만료와 `UNKNOWN`을 포함한 mock 전체 흐름 |
| FE-3 | Task 2H OpenAPI 연동 | 생성 타입 사용, mock/real API 전환 가능 |
| FE-4 | Redis 대기열 SSE 연동 | 재연결·polling 폴백·토큰 만료 처리 |
| FE-5 | Playwright와 포트폴리오 산출물 | 핵심 E2E, 데스크톱·모바일 스크린샷, 짧은 시연 영상 |

FE-0~2는 MSW로 백엔드 API와 병행할 수 있지만, 실제 연동은 Task 2H 계약 뒤에 진행한다.

## 10. 포트폴리오 화면

README에는 다음 결과 화면을 선별해 넣는다.

1. 대기 순번과 SSE 연결 상태
2. 열차 조회 결과와 판매 상태
3. 호차·좌석 선택 및 경쟁 좌석 갱신
4. 홀드 만료 카운트다운과 결제 요약
5. 결제 `UNKNOWN`에서 최종 상태로 수렴하는 과정
6. 예약 완료와 Playwright E2E 결과

스크린샷만으로 구현된 기능을 과장하지 않는다. mock 화면은 `MSW demo`, 실제 연동 화면은
`integrated`로 구분하고, README의 현재 구현 표와 함께 갱신한다.
