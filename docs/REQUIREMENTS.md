# RailGate — 요구사항

> 상태: 초안 v0.2 (2026-08-31)
> `가정` = 근거 없이 설정한 값. 실측 후 갱신 대상.
> `결정 필요` = 아직 확정하지 않은 정책.

---

## 1. 목적과 범위

명절 기차 예매처럼 특정 시점에 수십만~수백만 명이 동시 접속하는 환경을 가정하고,
**공정한 선착순 처리**와 **좌석 정합성**을 구현·검증한다.

실제 예매 시스템을 우회하거나 자동화하려는 목적이 아니다.
공정한 예매 시스템의 내부 동작을 이해하고, 그 동작을 측정으로 입증하는 것이 목적이다.

## 2. 기능 요구사항

### FR-1. 대기열

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1.1 | 사용자는 예매 이벤트 대기열에 등록하고 순번을 발급받는다 | MVP |
| FR-1.2 | 발급된 순번은 단조 증가하며 재사용되지 않는다 | MVP |
| FR-1.3 | 유효 엔트리 보유 중 재등록 요청은 **기존 순번을 그대로 반환**한다 (새 순번 발급 금지) | MVP |
| FR-1.4 | 사용자는 자신의 순번, 앞 대기 인원, 예상 대기 시간을 조회한다 | MVP |
| FR-1.5 | 순번 변화는 SSE 로 push 하며, 폴링 API 를 폴백으로 제공한다 | MVP |
| FR-1.6 | 사용자는 대기를 취소할 수 있다 | MVP |
| FR-1.7 | Admission Scheduler 가 주기적으로 대기열 앞부분을 Active 로 승격한다 | MVP |
| FR-1.8 | 승격된 사용자는 입장 토큰을 발급받는다 | MVP |
| FR-1.9 | 엔트리와 Active 세션은 각각의 TTL 로 만료된다 | MVP |
| FR-1.10 | 관리자는 이벤트 오픈/마감과 입장 속도를 조정한다 | 후속 |

**정확도 요구사항 (FR-1.4 상세)**
앞 대기 인원은 취소·만료로 생긴 구멍 때문에 정확한 값을 O(1) 로 계산할 수 없다.
따라서 응답에 정확도를 명시한다.

- `precision: ESTIMATED` — 통계 보정된 추정치. 대부분의 사용자
- `precision: EXACT` — 실제 값. 앞 대기 1,000명 미만인 사용자에게만 제공

### 오류율 정의 (중요)

| 응답 | 오류율 포함 여부 |
|---|---|
| 5xx / 타임아웃 | ✅ 포함. **< 0.1%** |
| `409` 좌석 경합 실패 | ❌ **미포함.** 정상 동작이며 경합 시 90%도 정상 |
| `429` rate limit / 입장 제한 | ❌ 미포함 |
| `202` 결제 결과 미확정 | ❌ 미포함 |

> 409 를 오류로 집계하면 지표 전체가 거짓이 된다. k6 threshold 설정 시 반드시 분리한다.

## 4. 트래픽 모델 (전부 `가정`)

**시나리오 `가정`:** 단일 예매 이벤트, 열차 100편 × 500석 = 총 50,000석.

| 항목 | 프로덕션 목표 모델 | 로컬 검증 모델 (1/20) |
|---|---|---|
| 전체 대기 사용자 | 1,000,000명 | 50,000명 |
| 대기열 등록 TPS (피크) | 20,000 | 1,000 |
| 순번 조회 (순진한 구현) | 200,000 TPS | 10,000 TPS |
| 순번 조회 (목표) | Redis 도달 < 10 TPS | 동일 |
| 동시 SSE 커넥션 | 200,000 | 10,000 |
| 목표 Active 사용자 | 5,000 | 250 |
| 초당 입장 허용 | 55명/s | 3명/s |
| 좌석 조회 TPS | 2,500 | 125 |
| 좌석 선점 TPS | 150 (피크 300) | 8 (피크 15) |
| 동일 인기 좌석 경합 | 1,000 (테스트값) | 1,000 (축소하지 않음) |
| 결제 TPS | 60 (피크 150) | 3 |
| 총 좌석 | 50,000석 | 2,500석 |

> **⚠️ 로컬 Docker Compose 에서 프로덕션 TPS 는 달성 불가능하다.**
> k6·앱·MySQL·Redis 가 같은 CPU 를 나눠 쓰면 **k6 자신이 병목**이 되어 병목을 오독한다.
>
> - **외삽 가능 지표:** 요청당 Redis 명령 수, 요청당 쿼리 수, 요청당 바이트
> - **외삽 불가 지표:** 절대 TPS, 절대 p99
>
> 결론은 반드시 다음 형식으로만 서술한다:
> *"1/20 축소 환경에서 X TPS, 자원 사용률 Y% → 선형 외삽 시 Z TPS 추정(미검증)"*

## 5. MVP 범위

### 반드시 포함

- 좌석 조건부 UPDATE 선점 + 다중 좌석 원자성
- 1인당 선점 상한 (카운터 행 방식)
- 멱등성 키 인프라 (리스 방식, 3단 트랜잭션 경계)
- 선점 만료 스위퍼 (`hold_id` CAS, id 정렬)
- Mock PG authorize/capture + `UNKNOWN` 재조회 (`merchantRef` 기반)
- Redis 대기열 (Lua 원자 등록/승격) + 입장 토큰 + SSE
- 동시성 테스트 9종
- k6 부하 테스트 + 정합성 검증 쿼리 자동화
- Consistency Guard 대시보드
- 검색·대기열·좌석 선택·홀드·결제·예매 내역을 잇는 사용자 웹

### 후속 단계로 미룸

| 항목 | 시점 | 이유 |
|---|---|---|
| Kafka + Outbox/Inbox | Phase 4 | MVP 동작에 불필요. 기동 시간·테스트 복잡도만 증가 |
| 예약 취소 / 환불 | Phase 5 | 정합성 코어가 안정된 뒤 |
| Redis 대기열 샤딩 | Phase 6 | **측정 전 도입은 근거 없는 복잡도** |
| WebFlux vs Virtual Thread 비교 | Phase 6 | 벤치마크 프로토콜 확립 후 |
| MySQL read replica | Phase 6 | 병목 실측 후 |
| 클라우드 배포 | Phase 7 | 절대 TPS 를 주장할 수 있는 유일한 단계 |
| 관리자 웹 UI | 후속 | |
| 환승·다구간 예매, 할인/쿠폰 | 후속 | 정합성과 무관한 비즈니스 확장 |

### 하지 않을 것 (명시적 범위 제외)

- **Event Sourcing / CQRS** — 이 도메인에 이득 없이 복잡도만 폭증
- **Saga 오케스트레이션 프레임워크** — 트랜잭션이 한 DB 에서 끝나므로 불필요
- **서비스 메시(Istio)** — 서비스 2개에 과도
- **gRPC 내부 통신** — 서비스 간 동기 호출이 0회이므로 대상 자체가 없음
- **자체 API Gateway 개발** — Nginx 로 충분
- **멀티 리전 / 글로벌 복제**
- **전 좌석 실시간 WebSocket 동기화** — 좌석 5만 개 브로드캐스트는 별개의 대규모 문제
- **네이티브 모바일 앱** — 반응형 웹으로 MVP 사용자 흐름을 먼저 검증

**판단 기준:** *"이 기능이 불변식을 지키거나, MVP 예매 흐름과 그 보장을 사용자에게
검증 가능하게 만드는가?"* 둘 다 아니면 나중으로 미룬다.

### P-4 상세 — 선점 만료 시각 정책

**최종 만료 시각은 절대 앞당겨지지 않는다.**

```
HELD  진입: expires_at = NOW(3) + 5분
PAYING 진입: expires_at = max(기존 expires_at, NOW(3) + 5분)
SOLD  진입: expires_at = NULL
```

| 상황 | 결과 |
|---|---|
| 결제 데드라인이 기존 만료보다 **뒤** | 그 시각까지 **연장** |
| 결제 데드라인이 기존 만료와 **같음** | 기존 값 **유지**. 거부하지 않음 |
| 결제 데드라인이 기존 만료보다 **앞** | 기존 값 **유지**. 거부하지 않음 |

**더 이른 데드라인을 거부하지 않는 이유.**
결제 창(5분)이 홀드 잔여 시간보다 짧아지는 순간이 존재한다. 예를 들어 홀드 만료가 `T+5:00`
인데 사용자가 `T+0:30`에 결제를 시작하면 `NOW(3)+5분 = T+5:30`이라 연장되지만,
`T+0:10`에 시작하면 `T+5:10`, 정책상 5분이 아니라 3분짜리 결제 창을 쓰는 구성이라면
`T+3:10 < T+5:00`이 되어 **정상 요청이 실패**한다.
정책의 목적은 *만료를 앞당기지 않는 것*이지 *요청을 거부하는 것*이 아니다.

**책임 분담.**

| 계층 | 역할 |
|---|---|
| 도메인 (`Seat.startPayment`) | `max()` 계산으로 만료가 앞당겨지는 것을 **구조적으로 불가능**하게 만든다. 현재 시각을 모르므로 두 시각의 상대 관계만 다룬다 |
| 인프라 (TASK-2) | **이미 만료된 홀드의 결제 시작을 막는 최종 방어선** |

```sql
-- 최종 방어선. 도메인은 이 조건을 대신할 수 없다.
UPDATE seat_inventory
   SET status='PAYING',
       expires_at = GREATEST(expires_at, NOW(3) + INTERVAL 5 MINUTE)
 WHERE id = ?
   AND hold_id = ?
   AND status = 'HELD'
   AND expires_at > NOW(3);
-- affected_rows = 0 → 이미 만료됐거나 다른 사용자가 가져갔다 → 409
```

`NOW(3)`을 쓰는 이유는 CLAUDE.md 규칙 7이다. 애플리케이션 시각을 쓰면 인스턴스 간
클럭 드리프트로 만료 판정이 갈린다. 도메인 코드는 `Instant.now()`를 호출하지 않는다.

### 확정 시 홀드 소멸

`SOLD` 전이는 `hold_id`, `held_by`, `expires_at`을 모두 비운다.

홀드는 *만료될 수 있는 임시 점유*이고 확정된 좌석에는 그런 것이 존재하지 않는다.
홀드 이력이 필요하면 `seat_state_log`에 남기고 활성 상태 필드에는 남기지 않는다.

**두 가지를 혼동하지 않는다.**

| | 역할 |
|---|---|
| `expires_at = NULL` | **상태 조합을 명확하게 유지한다.** SOLD에 의미 없는 필드를 남기지 않아, 복원 검증이 손상된 행을 즉시 잡아낼 수 있다 |
| 스위퍼의 `status IN ('HELD','PAYING')` | **I-11을 지키는 최종 방어선.** SOLD를 상태 술어로 배제하므로 `expires_at` 값과 무관하게 확정된 좌석은 회수되지 않는다 |

`expires_at`을 비우는 것은 I-11의 방어 수단이 **아니다**. `expires_at`이 남아 있어도
스위퍼 조건이 SOLD를 이미 제외하므로 I-11은 유지된다. 비우는 이유는 정합성 표현이지
안전장치가 아니며, 스위퍼 조건에서 상태 술어를 빼면 아무것도 막지 못한다.

소유권 검사는 **상태를 바꾸기 전에 기존 `hold_id`로** 수행한다. SQL에서는 `WHERE`가
기존 값을 읽고 `SET`이 지우므로 순서가 자연히 보장된다.

```sql
UPDATE seat_inventory
   SET status='SOLD', reservation_id=?, hold_id=NULL, held_by=NULL, expires_at=NULL
 WHERE id=? AND hold_id=? AND status='PAYING';
```

## 7. 알려진 모호함 · 충돌

| 항목 | 내용 |
|---|---|
| **공정성 vs 확장성** | 대기열 샤딩은 처리량을 올리지만 전역 FIFO 를 깬다. 둘 다 만족하는 방법은 없다. **얼마나 잃는지 역전율로 정량 측정**하는 것이 답 |
| **정확한 순번 vs 폴링 부하** | 정확한 순번은 O(log N), 추정치는 O(1). 전 사용자에게 정확한 값을 줄 수 없다 → `precision` 필드로 명시 |
| **만료 후 재등록 정책** | "맨 뒤로" 는 공정하지만, 사용자 잘못이 아닌 네트워크 장애로 만료된 경우와 구분 불가 |
| **1인당 상한 vs 가족 예매** | 4석 상한은 5인 가족을 배제한다. 실제 서비스라면 정책 예외가 필요하나, 이 프로젝트에서는 다루지 않는다 |
| **Mock PG 의 현실성** | 실제 PG 의 실패 모드를 완전히 재현하지 못한다. 재현 범위를 문서에 명시하고 그 밖은 주장하지 않는다 |
